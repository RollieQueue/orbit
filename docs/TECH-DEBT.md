# Технический долг Orbit (после 0.4.0)

Список того, что решено, но не сделано. Порядок — по важности для владельца.

## 1. Автоматический перезапуск с продолжением задачи из любого чата

**Проблема.** Orbit запускается из репозитория, но новый код (в том числе новый навык или инструмент, который агент
только что написал и проверил) вступает в силу только после перезапуска процесса. Сегодня перезапуск умеет делать
лишь `npm run self-upgrade`, и после него никто не продолжает прерванный запуск: агент, который затеял изменение,
остаётся в состоянии `interrupted`, а следующее сообщение в чат должен отправить человек. Сценарий владельца:
«я попросил что-то сделать, агент придумал себе навык, реализовал, проверил, а применить не может, потому что для
этого надо перезапуститься».

**Что нужно.**

1. Инструмент Orbit `restart_orbit { reason, continueWith }` (только корневой агент, любой чат, любой провайдер):
   - runtime записывает *намерение продолжить* в `userData/pending-resume.json`: `projectId`, `chatId`, `runId`,
     `agentId`, текст `continueWith` (что делать после перезапуска), время и причину;
   - сбрасывает состояние на диск (как `before-quit`), завершает текущий запуск с пометкой `restarting` (не
     `interrupted`), и запускает тот же путь, что и `self-upgrade`: отдельный процесс-наблюдатель → `--relaunch` →
     файл здоровья → откат при неудаче. Проверки (typecheck/тесты) перед перезапуском — по флагу `verify: true`
     (по умолчанию включён, иначе сломанный код уронит приложение; откат по health-файлу остаётся страховкой).
2. После здорового старта `main.cjs` читает `pending-resume.json`, удаляет его и **сам** начинает новый ход в том
   же чате: промпт = `continueWith` + служебная строка «Orbit перезапущен с новым кодом (коммит …, причина …);
   предыдущий запуск завершён перезапуском, его история в дайджесте». Дайджест предыдущих ходов, память, навыки
   и список файлов уже попадают в промпт через существующий механизм `Chat team memory`.
3. Если перезапуск откатился, продолжение не запускается; вместо него в чат публикуется заметка с причиной
   и путём к `artifacts/self-upgrade-failed.patch`, чтобы агент (или человек) мог починить.
4. `scripts/self-upgrade.cjs`, запущенный из-под агента, делает то же самое: runtime передаёт командам агентов
   `ORBIT_CHAT_ID`/`ORBIT_RUN_ID`/`ORBIT_PROJECT_ID` в окружении, скрипт по ним пишет то же намерение.
5. Защита от зацикливания: действующее окно `ORBIT_UPGRADE_MAX_CYCLES` за `ORBIT_UPGRADE_CYCLE_WINDOW_MIN`
   минут распространяется и на `restart_orbit`; продолжение после третьего подряд перезапуска не запускается,
   а в чат пишется предупреждение.
6. Интерфейс: заметка в чате «перезапущен по запросу агента, задача продолжена», в панели агента — связь
   между запуском до и после перезапуска (`resumedFrom: runId`).

**Проверка.** Тест на runtime с фиктивным перезапуском (намерение записано, запуск помечен `restarting`); тест
`main-load` на чтение намерения и запуск хода; сценарий на настоящем Electron: агент вызывает `restart_orbit`,
процесс перезапускается, в том же чате появляется продолжение с новым кодом. Оценка: 1–2 дня.

## 2. Runtime в дочернем процессе: перезапуск без закрытия окна

Сейчас перезапуск закрывает окно на 1–2 секунды. Если вынести runtime (всё `electron/runtime/*` и провайдеры)
в дочерний процесс Node, окно остаётся открытым, runtime перезапускается быстрее секунды, а полный перезапуск
нужен только для правок оболочки (`main.cjs`, `preload.cjs`, `ipc-*.cjs`). Естественное продолжение пункта 1.

## 3. Дотипизировать runtime

18 файлов `.mts` ещё под `// @ts-nocheck` (список в `docs/TYPESCRIPT-MAIN.md`, «Remaining work»); в
`electron/ipc-handlers.cjs` два приведения к `any` из-за расхождения `StoredRun`/`FileChange` между
`run-store.mts` и `types.mts`. Всё остальное проходит `strict`.

## 4. Сессионный режим для Cursor и Antigravity

Оба работают по старому протоколу конверта: каждый инструмент Orbit — новый процесс, у Antigravity нет нативных
инструментов (чтение файла — ход по 200 строк). У Cursor есть MCP через `~/.cursor/mcp.json`, у Antigravity —
`--input-format stream-json`; нужно проверить, что из этого даёт сессию с MCP.
