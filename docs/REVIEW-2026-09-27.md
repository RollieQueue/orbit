# Проверка предложений консилиума

Проверено по текущим исходникам 27 сентября 2026 года. В целом направления верные, но часть механизмов уже существует. Это оценка и порядок дальнейших работ, а не заявление о реализации всех пунктов.

| Предложение | Оценка по коду | Приоритет |
| --- | --- | --- |
| Единый валидируемый service-layer для IPC | Согласен. В `electron/main.cjs` остаётся прямой `providers:ask → runProvider`; `preload.cjs` открывает его renderer. В обход runtime теряются единая политика, учёт и остановка. Нужны схемы входов и единый путь исполнения для привилегированных действий. | Первый этап |
| Onboarding-чеклист | Согласен. Проверка провайдеров, подключение проекта и настройки есть, но нет единого состояния готовности. Выбор конкретной модели не должен быть обязательным: корректно работает модель по умолчанию CLI. Тестовый запрос должен запускаться явно и сообщать о расходе квоты. | После исправления запуска |
| Прозрачные права | Согласен. Наследование прав уже есть и проверяется тестами. Нужно яснее показывать фактические ограничения каждого провайдера, папку проекта, команды, сеть и политику подтверждения. | Первый этап |
| Полноценный sandbox | Согласен с целью. `runtime-tools.cjs` проверяет файловые пути, но команды работают с правами пользователя ОС. Отдельный процесс сам по себе не sandbox; нужны ограничения ОС и отдельная проверка Windows. Full access должен оставаться явно выбранным режимом. | Отдельный проект, высокий приоритет |
| Окружение и исходящий трафик | Согласен. CLI наследуют `process.env`, endpoint допускает HTTP. Для внешних адресов нужны HTTPS и политика разрешённых адресов/редиректов. Локальный HTTP для Ollama/локального API нужно сохранить. Allowlist окружения вводить отдельно для пользовательских команд и провайдеров, сохраняя необходимые переменные авторизации и запуска. | Первый этап |
| Завершение и восстановление | Согласен. Отмена дерева процессов и отметка interrupted уже есть, но `before-quit` не ожидает завершения операций. Нужен асинхронный shutdown с запретом новых запусков. Повторение/продолжение должны создавать понятный новый запуск из сохранённой истории и не повторять выполненные действия вслепую. | Первый этап |
| Транзакционное хранилище | Согласен. Сейчас JSON с временным файлом, rename и резервной копией — защита лучше простой перезаписи, но нет транзакции между чатами, запусками и памятью. RunStore ограничивает записи в памяти, однако не удаляет старые файлы с диска. Сначала миграция/восстановление и retention, затем SQLite или журнал. | Второй этап |
| События и производительность UI | Согласен частично: отдельные события уже передаются, потоковый вывод объединяется, снимки записываются с задержкой. Не хватает sequence/replay, ограничения стоимости снимков и виртуализации длинных списков. Переключатель инспектора в этом исправлении уже закреплён. | Второй этап, по измерениям |
| Context Manager | Согласен. Лимиты сейчас символьные, старые наблюдения обрезаются, используется `JSON.stringify` в цикле и линейный поиск памяти. Нужны счётчики, оценка токенов по провайдеру и сохраняющая обязательные инструкции суммаризация; универсальный точный токенизатор для всех провайдеров обещать нельзя. | Второй этап |
| Доверие к памяти, навыкам и провайдерам | Согласен. Уже есть scope-проверки, частичная редакция секретов, source, десять ревизий навыка и восстановление. Не хватает просмотра diff, более строгого происхождения и политики глобальных изменений. Fixtures и desktop-smoke уже есть; их стоит закрепить в CI и добавить реальные версии контрактов провайдеров. | Политика доверия — первый этап; CI/контракты — второй |

## Причины текущих ошибок и исправление

Старая проверка в `OrbitRuntime.start` запрещала второй записывающий запуск во всём проекте. Теперь разные чаты могут работать одновременно. Файлы общие, поэтому это не гарантия от конфликтов двух изменений одного файла. Повторный запуск в том же чате и запуск во время остановки незавершённых записывающих процессов по-прежнему блокируются.

В сохранённом запуске консилиума обнаружены ошибка `collab spawn failed: no thread with id`, последующие завершённые нативные вызовы `spawn_agent` и только корневой агент в снимке Orbit. Это подтверждает расхождение двух механизмов делегирования. Старая история не содержит достаточных данных, чтобы достоверно восстановить дерево и переписку этих подагентов.

В обоих адаптерах Codex отключено встроенное делегирование только для запускаемого процесса. Делегирование идёт через Orbit, где уже реализованы дерево, обмен сообщениями, лимиты и отмена. Инструкция уточняет, что JSON-вызов инструмента должен завершать ход, а не выводиться промежуточным комментарием. Форматы конфигурации и доступных кратких размышлений сверены с [OpenAI Docs: config reference](https://learn.chatgpt.com/docs/config-file/config-reference) и [App Server](https://learn.chatgpt.com/docs/app-server).

## Проверки

- 63 автоматических теста: runtime, провайдеры, IPC transport fixtures и хранилища.
- Typecheck и production build.
- Настоящий Electron в отдельном временном профиле: два записывающих чата одного проекта работают одновременно, ответы не смешиваются; дерево и переписка восстанавливаются после reload; вкладки остаются на месте при реальном скролле.
- Настоящий Codex с обычной просьбой создать помощника: два агента завершились, помощник вычислил 19×23=437 и отправил сообщение родителю; дерево и события сохранены. Нативных CLI-подагентов не было.
