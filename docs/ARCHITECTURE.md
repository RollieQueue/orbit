# Orbit harness contract

```text
React: projects → task chats → optional agent inspector
                      │ typed preload IPC
Electron main:        ├─ state, memory, capabilities, run history
                      └─ OrbitRuntime
                          ├─ root agent ↔ model/tools
                          ├─ child ↔ model/tools → grandchildren
                          └─ replaceable provider adapters
```

## Model-driven execution

There is no intent classifier, fixed specialist pipeline, mandatory repository scan or simulated answer. A user message starts one root agent. Its prompt includes a stable identity, bounded conversation history, relevant memory, a capability index, access rules and tool descriptions.

```text
session   (Claude Code, Codex)          envelope   (Cursor, Antigravity, Ollama, custom endpoints)
  one CLI session per agent               one fresh provider process per turn
  turn 1: system block + full prompt      every turn: the whole assembled prompt
  Orbit tools over MCP, mid-turn          Orbit tools as a JSON envelope ending the turn
  later turns: --resume + what is new     observations appended, model called again
```

**Two transports.** Each agent runs on one of two transports, decided when it is created from its provider (`providers.transportFor`; `ORBIT_LEGACY_ENVELOPE=1` forces the envelope everywhere; a runtime built with a custom `runProvider`, as tests and embedders do, uses the envelope unless it injects its own `transportFor`). *Session*: the first turn sends a stable block appended to the provider's system prompt (identity, access, delegation and memory rules, how Orbit's tools differ from native ones; at most 6 000 characters, nothing that changes between turns) and a user prompt with the task and everything the envelope prompt carries (memory, skills, shared context, index overview, chat digest, team roster, FILE MAP). Orbit's tools are served to the provider by the in-process MCP server (`mcp-server.mts`, started lazily on the first session; one bearer token per agent execution, revoked when it ends; when the server cannot start the agent falls back to the envelope with a trace). A call arrives at `runtime.dispatchMcp(token, name, args)`, runs through `executeTool` with the same ledger, work-log, file-activity, change-capture and trace side effects as an envelope call (the observation is also kept in the transcript, marked `via: 'mcp'`, and never re-sent), and returns the observation text plus the agent's unread-mail count, which the server appends as a suffix. A waiting tool (`wait_agent`, `wait_message`, `followup_agent`) releases the agent's model slot while it blocks and takes it back before answering; mail the running turn's prompt already carried is not "pending" during that turn. The text a turn returns is an answer candidate. Post-answer checks run in this order, each at most once per candidate, each a resume of the same session carrying only what is new (the instruction, helper results, follow-up tasks, mail): helpers still running or results not yet seen → wait, then resume; unread mail → resume; completed workers not yet evaluated → one combined `model_evaluate` reminder; improvement mode not closed → the existing continuation (three reminders, then the answer with a note); skill learning → the single reminder. A resume that fails delivers the candidate. No process is killed at a tool call and no prompt is re-sent. A finished session agent woken later by a message or a follow-up resumes its own session. *Envelope*: each model response is either a normal final answer or an explicit JSON tool envelope. The runtime parses the complete envelope (not arbitrary JSON embedded in prose), dispatches declared tools, attaches observations and calls the model again with the whole prompt. The tool descriptions come from `tool-registry.mts` (`describeForPrompt`) when that module is present and are otherwise the runtime's inline text, unchanged. Codex and Claude can also use their native tools on either transport; their streamed execution events are exposed as traces. Orbit-created agents form the inspectable tree; agents created internally by a vendor's own tools remain vendor trace events.

A subscription handover (see below) can cross transports: the note is built from the ledger; a replacement on the session transport starts a fresh session with the note and the transcript in its first prompt, one on the envelope transport continues the envelope loop from the same transcript. Cancellation kills the provider process tree on both; when a run ends, whatever a provider keeps alive between turns (a Codex App Server thread) is closed. Every provider turn leaves a record in `agent.turnTimings[]` (`turn`, `transport`, `startedAt`, `firstEventAt`, `endedAt`, `promptChars`, `nativeToolCalls`, `orbitToolCalls`, `sessionId`), persisted with the run and echoed in the `run.info` event that ends the turn; `agent.transport` and `agent.sessionId` are public agent fields, the bearer token never leaves the runtime. The root agent's answer in progress is published as `message.streaming` (`runId`, `projectId`, `chatId`, `agentId`, `messageId`, `content` = the whole text so far; at most four times a second); the final `message.added` reuses that `messageId`. A tool envelope being typed in envelope mode never streams.

The runtime provides file operations, subprocess execution, durable memory, reusable capabilities and swarm operations. The model decides which operations to use. `spawn_agent` requires a concrete task and reason. Every child runs the same loop with its own context and can delegate further. Parent agents receive child results and integrate them. Model-call concurrency slots are released before tool calls and waiting, so a parent does not occupy the slot a child needs to finish.

Agent communication also belongs to the harness, so it works across different providers. `send_message` targets another member of the same run, including siblings and parents. `read_messages` and `wait_message` let agents read or await correspondence. Delivery occurs at a model-turn boundary; an already running vendor inference is not secretly modified. Waiting releases the model slot. `followup_agent` resumes an eligible finished helper with a new assignment and preserved context under the same shared budget. The team correspondence is recorded separately from messages addressed to the user and exposed in the agent panel.

## Team traffic: router, file activity, project index

```text
agent A ──send_message / ask_team──▶ router ──▶ agent B (mailbox, next turn boundary)
   │                                   ▲
   └─ read/write ─▶ file activity ─────┘  who touched what → audience, notices, conflicts
```

The **router** (`router.mts`) is the single path for agent-to-agent messages. It is a deterministic dispatcher, not a model call: it costs no provider turn or slot and cannot start a conversation of its own. `ask_team` resolves the audience without ids: explicit `agentIds`, the author of `replyTo`, agents that changed (weight 10) or read (4) the named files or folders, agents whose name/task/touched files match the topic (score at least 3, at most three recipients, active agents first); with no match a worker's question escalates to its parent and the root gets an error. Every message, including plain `send_message`, passes `pass()`: an exact repeat to the same recipient is refused, and a pair that exchanged six messages without either side making progress (a successful write or edit, a delegation, a native file change or a command's attributed changes — `agent.workDone`) is closed until one of them does something. Saving a note or another message does not reopen it, so polite chatter cannot loop.

When an agent changes a file, the router posts a `notice` communication to every other *active* agent that read or changed it (finished agents are neither woken nor told). Notices from one writer to one reader coalesce while unread and are deduplicated per reader turn. Two writers on one file produce a conflict notice. Notices are information: they never count as messages for `maxMessages`, never wake a wait, and never keep an agent from finishing (`pendingMail` excludes them), so they cannot extend a run. Routing decisions are communications carrying `via: 'router'` and `route: { via, reasons }`, plus traces under the pseudo-participant `router`; the router is not in `agentNodes`, so no loop over agents (waiting for children, broadcasting, results) treats it as a worker.

**File activity** (`file-activity.mts`) records, per run, which agent read or changed which workspace path. Sources are Orbit's file tools (exact), provider events of native tools (Codex `file_change` `changes`, Claude `Read/Edit/Write` `input`; a native write counts only after a completed status, failed or declined ones are dropped) and files a `run_command` changed, attributed only when unambiguous (no overlapping command, no provider turn running, no other active chat in the folder, at most 40 files). It feeds each agent's public `files`, the FILE MAP in every turn's prompt, the `sharedWith` field of write results and the router.

The **project index** (`project-index.mts`) is a local, model-free index per workspace: path, size/mtime version, language, line count, up to 200 symbols with line numbers, imports (relative ones resolved into a dependency graph), a first-comment summary and the 60 most characteristic terms per file. Terms are stemmed the way memory notes are (`text-index.mts`: plural *s*, then five letters), and the words of the file's own symbols and first comment weigh three times a passing mention, so "refreshing indexes" reaches `refreshIndex` and a module is found by what it says about itself. File lists come from `git ls-files -co --exclude-standard` (run from a neutral working directory, because Windows locks a process's cwd; ignored bundles such as `Orbit-standalone-*` cost nothing because Git never lists them) or, when Git errors or lists nothing (a folder its parent repository ignores), a bounded walk that skips `node_modules`, build output and symlinks. Scans are incremental by size+mtime and deduplicated per workspace; an index loaded from disk is never considered fresh, and one written by an older analyzer version is rebuilt once. A path an agent touches that differs only in case from the listed one updates that entry on a case-insensitive disk. Content over 512 KB, generated and binary files are listed without content. Search is lexical over inverted lists of terms and of symbol words: path > symbol > IDF-weighted terms, one symbol hit per query word per file, and a test file ranks a little below the module it tests. The index file in `userData/project-index/` is a cache, written compact and without a backup copy: a damaged one costs one rescan. `index_search`/`index_outline` are read-only tools; the run starts a scan immediately and the first prompt waits for it for at most 2.5 s.

## Chat team memory

The UI's chat history contains only the root agent's words. At `start`, the runtime therefore collects the earlier runs of the same project and chat (in memory plus `RunStore.forChat`) and builds a digest for the root prompt: per earlier turn the request, the answer, each helper with task, result and touched files, and the latest team messages; the two newest turns in detail, older ones in one line, at most 6000 characters. Workers do not receive it. `team_history` returns the full reports within one observation's budget, and `spawn_agent { continueFrom }` seeds a new helper's "previous work" from an earlier agent. All of it comes from persisted run snapshots (agent `files` included), so it survives a restart. It is data the model must verify, not evidence that the files are still as they were.

## Subscription quotas and failover

```text
CLIs ──▶ quota.mts readers ──▶ QuotaMonitor (one per app) ──▶ window: "Квоты", chip, agent panel
             ▲   live events (Claude rate_limit_event, Codex rateLimits/updated)
runtime ── before each turn ──▶ assess(agent's provider, model) ──▶ near/exhausted? ──▶ failover.replacements ──▶ handover
   └────── on a refused turn ──▶ classifyQuotaError ──▶ markExhausted ──▶ handover, repeat the turn
```

**Readings** (`quota.mts`) come only from what a CLI itself reports; no OAuth token is read and no vendor HTTP API is called. Codex: the app-server request `account/rateLimits/read` (5-hour and weekly windows, plan, credits) and its rolling `account/rateLimits/updated` notifications. Claude Code: the text of `claude -p "/usage"`, a local command that neither calls a model nor spends quota (`num_turns: 0`), plus `rate_limit_event`s in the stream, whose `utilization` is a fraction of the window. Antigravity: the JSON of `agy -p "/usage"` (groups of models, each with a 5-hour and a weekly bucket). Cursor: `agent about` names the plan and nothing else. Ollama is unmetered and a custom endpoint publishes nothing. A snapshot is a list of windows `{ kind, usedPercent, resetsAt, scope, models }`; `models` limits a window to model-name fragments (Claude's per-model weekly limits, Antigravity's groups), so `assess(snapshot, { model })` counts only the windows that bind that model, and a window whose reset time has passed counts as empty. `QuotaMonitor` caches for a minute, shares one refresh among concurrent callers, retries a failed read after 20 s while keeping the last good figures marked stale, and keeps a *refusal mark* per provider: after a refusal the provider is out of rotation until the reset time the vendor's message named (30 minutes when it named none, ended early if a fresh reading is measurably below its limits).

**A refusal** is recognised by type where the provider gives one (Codex `usageLimitExceeded`/`rateLimitExceeded`, Claude's rejected `rate_limit_event`) and otherwise by wording (usage/5-hour/weekly limit, 429, quota, RESOURCE_EXHAUSTED, credits depleted …). Context-window overflows, cancellations and timeouts are never refusals.

**Handover.** Every provider turn is a fresh inference and the agent's memory lives in Orbit (transcript, work log, files, team directory, mailbox), so an agent may change model between two turns without losing anything: `agent.providerId/model/reasoningEffort` change and the next prompt is built for the newcomer. What is added is an explicit note (`failover.handoverNote`) pushed into the transcript and the work log: who is replaced and why, the state (turns, files written and read, teammates running and finished, unread mail), the last actions, and, when a turn was cut off, the text it had streamed and the native tool actions it had started (they may already have taken effect, so the newcomer is told to verify before repeating). An agent that has done nothing yet just starts on the new subscription. Handovers are recorded on the agent (`agent.handovers`, persisted with the run) and announced by an `agent.handover` event, a trace and, for the root agent, a chat notice. A turn the failover repeats does not count against `maxTurns`/`maxTotalTurns`. Each agent changes subscription at most eight times.

**Choosing the replacement** (`failover.replacements`, pure). Candidates are the models of connected providers (the health list) plus the user's pool; the agent itself, failed candidates, providers that just failed to answer at all (excluded for the whole run for ten minutes), local models and endpoints (unless pooled) and providers at or past the switch threshold are left out. After a refusal a second, relaxed pass accepts providers that are near but not over their limit. Quality is compared by tier (`model-tiers.json`: 3 flagship, 2 strong, 1 light, 0 unknown) which follows naming conventions, not measurements, and places doubtful models low: a candidate needs the tier of the agent's model (its actual model, else a deliberately high per-provider baseline), one lower if the run allows weaker models, never a light one, and unknown models only from the pool. Order: pool first, then the closest tier (equal, better, weaker), then the most quota headroom. The reasoning level is kept only where the target offers it (Google models have none; Cursor encodes it in the model name; a pool entry's level wins). Settings (`quotaFailover`: on/off, switch point 50–99%, allow weaker) are taken per run; nothing happens without a `QuotaMonitor` (tests and embedders that do not pass one see the old behaviour).

Run limits cover total agents, nesting depth, simultaneous model requests, turns per agent, and total turns across a run. Context and observations are bounded. Reaching a limit produces an explicit failure or tool error. It never fabricates a completed review.

## Working memory and the loop guard

On the envelope transport every provider turn is a fresh inference: the prompt Orbit assembles is the agent's only memory. It has three parts. Fixed instructions and the compact shared context come first (stable prefix). A `WORK LOG` follows: one line per call the agent has executed (tool, target, outcome), kept for the life of the agent and bounded to the newest 60 entries plus a tally of older ones. The rolling transcript comes last and holds full observations. The transcript never drops below a floor (40 000 characters, 9 000 for Ollama/compatible endpoints) whatever the fixed part costs, so a requested `maxContextChars` that cannot hold the instructions plus a usable window is raised rather than spent on starving the history. When old entries scroll out, the log still records what they were. The transcript's size is tracked per entry as it grows, so trimming compares numbers instead of re-serialising the whole transcript after every observation. On the session transport the provider keeps the conversation itself; Orbit keeps the same ledger, work log and transcript (MCP observations included) for the handover note, the inspector, a fresh session after a handover and a switch to the envelope loop, but sends a resumed session only what is new.

A loop guard runs after every envelope tool turn. A call is a *repeat* when the same tool and arguments return the same result, compared after removing self-changing fields (turn counters, timestamps) and timings in output. A turn is *stale* when every call in it is a repeat; waits that really blocked are not counted. Two stale turns in a row add a directive to the transcript, four stop the agent with a partial result that lists its last actions and helpers' results, and its still-running descendants are cancelled. Any novel call resets the counter, so this is not a turn limit and long varied work is unaffected. Independently, eight consecutive turns that changed nothing (no write, delegation, message or saved note) add a nudge to conclude, and a harness reminder (`model_evaluate`, improvement mode) that the model ignores three times in a row is dropped. A *poll budget* catches what the loop guard cannot see because each answer differs: six consecutive envelope turns made only of `list_agents`, `read_messages`, `context_read` or waits add one nudge (per streak) to call `wait_agent` or `wait_message` once with a timeout instead; nothing is stopped for it. On the session transport the model's native loop owns tool repetition; the loop guard and the poll budget do not apply there.

## Attribution, persistence and cancellation

`start` accepts `projectId`, `chatId`, `workspace`, `prompt`, `history`, `providerId`, optional `model`, access policy, memory setting and limits. Events contain `runId`, `projectId` and `chatId` even when the renderer is displaying another chat.

Canonical events: `run.started`, `run.info`, `agent.created`, `agent.updated`, `agent.handover`, `trace.added`, `message.streaming`, `message.added`, `communication.added`, `change.added`, `run.finished`, `run.failed`, `run.cancelled`. Listeners receive one detached copy of each event (never live runtime state). Snapshots contain agents, traces (the newest 2 000), messages, execution settings and timestamps; while a run is active its file is rewritten at most once a second for a burst of events, the terminal event is written at once. The renderer associates root answers with the owning chat and subagent output with the inspector. Updates to a communication reuse its ID, so delivery updates do not duplicate messages.

Communication events and the snapshot's `communications` array retain sender, recipient, content, time and delivery state. Messages cannot cross into another run or project merely by naming an agent. The UI restores correspondence alongside the agent tree after a reload.

Runtime lives in Electron main, independent of the displayed chat. Durable snapshots survive renderer reloads and app restarts. Cancellation propagates through one run to its children and provider process trees. A restart marks previously active snapshots `interrupted`; saved history can be used in a new turn. This is not a daemon that survives closing Electron.

## Memory tiers, retrieval and skills

```text
chat     working notes of one task thread ──promoted when used again──▶ project
project  verified knowledge of one codebase ──the same note, word for word, in ≥2 projects──▶ global
global   what holds in every project: preferences, how-tos, model assessments
skills   procedures worked out in a task: per project or global, with a track record
```

**Tiers.** All notes live in `memory.json`; an entry's `scope` (`chat`, `project`, `global`), workspace (canonical path, case-folded on Windows) and chat id decide who can see it. A run sees its chat's notes, its project's notes and, when allowed, the global tier. Workers default to `memoryProfile: 'project'` (chat and project tiers); `project-global` adds the global tier. A project can switch shared memory off: it then neither reads nor writes the global tier (notes *and* skills), and its notes never contribute to sharing. Legacy records without a workspace stay on disk, invisible. Common token strings are redacted before anything is stored. The chat tier has two halves: the notes described here (what was decided or constrained, written by agents or by the user) and the digest of earlier turns described under *Chat team memory* (what the team did, derived from saved run snapshots, never stored as notes).

**Bounded growth.** Each tier has a cap (chat 40, project 250, global 200; skills 60 per project and 100 shared), and a note is cut to 1 500 (chat) or 4 000 characters when an agent saves it (the agent is told when that happens); a skill an agent saves is cut to 12 000. Every entry has a *value*: confidence, recency (half-life 7 days for chat notes, 120 for project, 365 for global; twice as long for decisions and preferences) and use (`uses`, logged once per run and only when a note really matched the task or was read on purpose, so unrelated fill-ins cannot keep themselves alive). Over the cap the least valuable entries go first, the oldest among equals. The user's own notes (and the notes an older version saved from the UI, recognisable by their confidence of 100) and pinned notes are protected: never evicted, merged away or promoted, and an agent can neither overwrite nor remove them (`memory_save` with their id is refused; a near-duplicate is reported as already known). Model assessments are the harness's own records: agents cannot overwrite or remove them either, but they are capped (60, newest kept) and are never merged. An agent's note that says what an existing note says (title overlap ≥ 0.5 and text overlap ≥ 0.65, Jaccard over stems) updates it instead of adding a copy. After every finished run `maintain()` runs without a model: chat notes older than 30 days expire, chat notes that were used twice (preferences: three times) and have confidence of at least 70 are promoted to the project, near-duplicates (≥ 0.8) merge, low-confidence entries nobody used age out, caps are enforced. Deleting a chat deletes its notes without promoting anything. Usage counters are written lazily (a few seconds after the change, and on quit); every structural change is written to disk before it becomes visible, so a failed write leaves the state as it was.

**Isolation.** Isolation is enforced by the harness, not left to the model's choice of scope. A request to save something *global* (a note, a skill) is checked by `scope-guard.mts`: the text must not contain the workspace's absolute path (as given, resolved, or in its long/short Windows form), its folder name (three characters or more, unless generic like `src` or `lib`), a relative path that exists in it (however written: `src/a.js`, `./src/a.js`, `@/src/a.js`, non-ASCII names; a path with a space in a segment is not recognised), or its git remote (`github.com/owner/repo` or the bare `owner/repo`, found in the repository above the workspace and behind a linked worktree's pointer file). The checks lean towards raising the alarm: if any of them fires, the note is saved to the project instead and the agent is told why. A worker with project-only memory, or a project with shared memory off, cannot write global memory, and its global skills are kept in the project. Model assessments and skill pitfalls stored globally are scrubbed of the workspace path, of files that exist in it, of its folder name and of its repository; a pitfall recorded in a project skill loses the absolute path at once and never travels to a shared skill if it named anything of the project. A shared skill records the projects that used it only as short hashes. The guard is a safety net, not a judge of meaning: a note that describes a project without naming any of the above still depends on the model choosing the right scope, which is why sharing by promotion is so strict.

**Sharing by promotion.** Only the same note, word for word (identical set of words, numbers included; order and case ignored), found in at least two projects, of type pattern, fact or preference, not written by the user, passing the guard for each project, moves to the global tier: "port 3000" and "port 8080", or npm and pnpm, are different notes however similar they read. It looks across all projects, so it runs when the first run after start-up finishes and then at most every six hours, and only projects the UI has reported as sharing take part (the renderer reports each project's switch when it changes and at start-up; a project nothing has reported is treated as not sharing; start-up housekeeping never shares). Project copies stay, but are hidden from prompts while the shared note is visible. In practice this catches notes that agents reproduce identically; the main route to global knowledge is an agent choosing the global scope, under the guard.

**Retrieval.** `text-index.mts` is a small in-process inverted index (BM25; title ×3; stems: plural *s* removed, then the first five letters, so *memories*/*memory* and *проекты*/*проекте* meet; identifiers split at camelCase and separators). It is derived data, rebuilt at load and updated per change. Each model turn builds the memory block from `recall()`: pinned entries first, then matches for the agent's task, then the most valuable of the rest, per tier, within 4 500 characters (chat 25 %, project 45 %, global 30 %, unused room flows on). The orchestrator always sees the six newest model assessments. What did not fit is listed by short id and title, with how many entries are stored in all, so the agent knows it exists; `memory_search` reads it in full. Tools: `memory_search`, `memory_save` (scope `chat`, `project` or `global`), `memory_forget`.

**Skills.** A skill (`capabilities.json`) is a versioned, self-contained procedure: name, description, `whenToUse`, instructions; the previous ten revisions are kept and restore creates a new version. On top of the text it carries a track record: `uses` (once per run), `successes`, `failures` (`worked`/`partial`/`failed` via `capability_feedback`), the pitfalls reported with failures, and the projects that used it. The prompt lists the skills that match the task (ranked by relevance, then reliability `(successes+1)/(successes+failures+2)`), a few proven ones, and how many more exist; `capability_search` finds the rest and `capability_read` loads one whole, however long, and counts the use. Agents are told to check skills before improvising a multi-step procedure. Learning is prompted once per run, at the moment the root agent would give its final answer: when the run took ten or more provider turns without saving a skill, or a skill was loaded and not rated, the draft answer is kept in the transcript and the root gets one reminder to rate those skills and save a new one if it worked out something reusable, then to confirm its answer. It is a nudge, not a requirement: an answer without a save is accepted, and if that extra turn fails or comes back empty the draft is delivered. It costs one model turn; `skillLearning: false` in the start payload (Settings → "Учиться на задачах") turns it off, and so does disabling memory. A skill that says what an existing one says (name overlap ≥ 0.66 and text overlap ≥ 0.7) improves it as a new version instead of duplicating (the agent is told which skill it changed); procedures that merely share words are separate skills. A skill the user wrote stays protected when an agent improves it, and an agent's claim to be the user, the harness or the promotion pass is ignored. Maintenance drops skills nobody used for 180 days and skills that keep failing (three failures, reliability under 0.25), enforces the caps and shares, under the same word-for-word rule as notes, a procedure that was worked out independently in several projects, used at least once and tied to none of them. Skills are text: nothing in them is executed automatically, and helper scripts are written and run through the ordinary, approved file and command tools. Orbit does not install a new executable of itself. Skills are independent of the *memory enabled* setting (which no UI control turns off); the shared-memory switch of a project does apply to them.

**Shared project notes.** `context_save` notes remain the project's code-knowledge cache with dependency hashes (see above); `project-context.json` holds per workspace only the notes (the Git fingerprint and folder counts an older version stored beside them are dropped on load), and what agents receive is the notes with their staleness plus the folder overview. The notes agents leave automatically (`agent:<chat>:<name>`, `progress:<chat>`) are working state of a chat that happens to live in the project's file, so they are budgeted per chat: 30 per chat, the four most recently active chats, 14 days. A busy chat cannot push out another chat's notes, and notes saved on purpose are never touched.

Atomic JSON writes and backup recovery are shared by state stores. Run snapshots are batched during activity and flushed at completion/shutdown. The source of truth is local application data, not transient React state or demo seed records.

## Access boundary

File tools reject traversal and symlink escapes outside the selected project. Read-only mode disallows harness command execution and file writes. Workspace-write mode permits subprocesses with the current OS user's rights; `cwd` is not an OS sandbox. Native CLI providers apply their own documented access settings. The harness does not claim that it can sandbox arbitrary programs merely by validating command text.

Different chats may run concurrently in the same project, including write tasks. They share files; this is not worktree isolation. Prompts include other active tasks in overlapping folders and require preserving concurrent changes. The UI shows other active chats. A chat accepts only one active turn, including process cleanup. Cancelled/failed write processes still block new writes in overlapping folders until their operations settle. Within a swarm, the model must assign disjoint write responsibilities. Old worktree helpers remain internal utilities, not the default execution path.

Codex native multi-agent tools are disabled per process (`features.multi_agent=false`) in both exec and App Server transports. Orbit owns delegation, messages, cancellation and persistence. Orbit tool envelopes must be returned as the final provider response; commentary JSON is not executed. This avoids the invisible native-agent tree and ephemeral-thread collaboration failures. Readable reasoning summaries supplied by Codex are attributed to their Orbit agent; the UI does not fabricate unavailable reasoning. Inspector navigation stays outside the scrolling activity/correspondence pane.

## Runtime module map

`electron/runtime.mts` is the facade: it owns the state (runs, listeners, stores, the MCP server) and keeps the public surface (constructor options, methods, events); every method delegates to one function in `electron/runtime/` that receives the runtime instance first and calls the other modules only through those public methods, so no module reaches into another's state and no two modules require each other.

| Module | Concern |
|---|---|
| `util.mts` | shared helpers and constants (`bounded`, the single `clip`, `abortable`, agent views) and `diagnostics(runtime, run, where, error)`: an error the runtime deliberately survives leaves a trace of kind `diagnostic` instead of vanishing in an empty catch; it never throws and a finished run keeps none |
| `envelope.mts` | the JSON tool envelope: parsing a model response into content and tool calls (`parseResponse`) |
| `prompts.mts` | every text an agent is told (envelope tool guide, session system block, harness reminders) and the per-turn prompt assembly (`context`, `promptForTurn`, `resumePrompt`, team roster, FILE MAP) |
| `ledger.mts` | the transcript with tracked sizes and trimming, the work log (`describeCall`) and the collection of helper results |
| `store.mts` | snapshots, coalesced persistence, events to listeners, traces, agent updates, chat messages |
| `lifecycle.mts` | a run from start to end: payload validation and limits, the run record and root agent, earlier turns of the chat, finish, fail, stop, knowledge housekeeping |
