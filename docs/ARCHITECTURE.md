# Orbit harness contract

```text
React: projects → task chats → optional agent inspector
                      │ typed preload IPC
Electron main:        │ the shell: window, dialogs, health reports, restarts; 8 channels of its own
                      │ runtime-protocol.mts messages (utilityProcess)
Runtime process:      ├─ state, memory, capabilities, run history, quotas, Orbit MCP server
                      └─ OrbitRuntime
                          ├─ root agent ↔ model/tools
                          ├─ child ↔ model/tools → grandchildren
                          └─ replaceable provider adapters
```

## Model-driven execution

There is no intent classifier, fixed specialist pipeline, mandatory repository scan or simulated answer. A user message starts one root agent. Its prompt includes a stable identity, bounded conversation history, relevant memory, a capability index, access rules and tool descriptions.

```text
session   (Claude Code, Codex; in Full access envelope   (Ollama, custom endpoints; Cursor and
           also Antigravity, opt-in Cursor)               Antigravity outside Full access)
  one CLI session per agent                     one fresh provider process per turn
  turn 1: system block + full prompt            every turn: the whole assembled prompt
  Orbit tools over MCP, mid-turn                Orbit tools as a JSON envelope ending the turn
  later turns: --resume + what is new           observations appended, model called again
```

**Two transports.** Each agent runs on one of two transports, decided when it is created from its provider (`providers.transportFor`; Cursor and Antigravity get the session only in Full access, Cursor only when opted in, see docs/providers.md; `ORBIT_LEGACY_ENVELOPE=1` forces the envelope everywhere; a runtime built with a custom `runProvider`, as tests and embedders do, uses the envelope unless it injects its own `transportFor`). *Session*: the first turn sends a stable block appended to the provider's system prompt (identity, access, delegation and memory rules, how Orbit's tools differ from native ones; at most 7 500 characters, nothing that changes between turns) and a user prompt with the task and everything the envelope prompt carries (memory, skills, shared context, index overview, chat digest, team roster, FILE MAP). Orbit's tools are served to the provider by the in-process MCP server (`mcp-server.mts`, imported and started lazily on the first session; one bearer token per agent execution, revoked when it ends; when the server cannot start the agent falls back to the envelope with a trace). A call arrives at `runtime.dispatchMcp(token, name, args)`, runs through `executeTool` with the same ledger, work-log, file-activity, change-capture and trace side effects as an envelope call (the observation is also kept in the transcript, marked `via: 'mcp'`, and never re-sent), and returns the observation text plus the agent's unread-mail count, which the server appends as a suffix. A waiting tool (`wait_agent`, `wait_message`, `followup_agent`) releases the agent's model slot while it blocks and takes it back before answering; mail the running turn's prompt already carried is not "pending" during that turn. `wait_agent` and `wait_message` serve the turn that called them: they end with it (`ActiveTurn.signal`: a pause or a message cut it off, it finished) and take what they found (mail marked read, helper results marked seen) only once the turn has its slot back and still runs (`ready`), so a wait the turn left behind takes nothing and the next turn gets that mail as the user's words and those results as helper results; with no turn running a wait is refused. The text a turn returns is an answer candidate. Post-answer checks run in this order, each at most once per candidate, each a resume of the same session carrying only what is new (the instruction, helper results, follow-up tasks, mail): helpers still running or results not yet seen → wait, then resume; unread mail → resume; completed workers not yet evaluated → one combined `model_evaluate` reminder; improvement mode: the run's task not closed or not applied (see *Endless improvement loop*) → a specific reminder (three at most, then the answer with a note); skill learning → the single reminder. A resume that fails delivers the candidate. No process is killed at a tool call and no prompt is re-sent. A finished session agent woken later by a message or a follow-up resumes its own session. *Envelope*: each model response is either a normal final answer or an explicit JSON tool envelope. The runtime parses the complete envelope (not arbitrary JSON embedded in prose), dispatches declared tools, attaches observations and calls the model again with the whole prompt. The tool descriptions come from `tool-registry.mts` (`describeForPrompt`) when that module is present and are otherwise the runtime's inline text, unchanged. Codex and Claude can also use their native tools on either transport; their streamed execution events are exposed as traces. Orbit-created agents form the inspectable tree; agents created internally by a vendor's own tools remain vendor trace events.

A subscription handover (see below) can cross transports: the note is built from the ledger; a replacement on the session transport starts a fresh session with the note and the transcript in its first prompt, one on the envelope transport continues the envelope loop from the same transcript. Cancellation kills the provider process tree on both; when a run ends, whatever a provider keeps alive between turns (a Codex App Server thread) is closed. Every provider turn leaves a record in `agent.turnTimings[]` (`turn`, `transport`, `startedAt`, `firstEventAt`, `endedAt`, `promptChars`, `nativeToolCalls`, `orbitToolCalls`, `sessionId`), persisted with the run and echoed in the `run.info` event that ends the turn; `agent.transport` and `agent.sessionId` are public agent fields, the bearer token never leaves the runtime. The root agent's answer in progress is published as `message.streaming` (`runId`, `projectId`, `chatId`, `agentId`, `messageId`, `content` = the whole text so far; at most four times a second); the final `message.added` reuses that `messageId`. A tool envelope being typed in envelope mode never streams.

The runtime provides file operations, subprocess execution, durable memory, reusable capabilities and swarm operations. The model decides which operations to use. `spawn_agent` requires a concrete task and reason. Every child runs the same loop with its own context and can delegate further. Parent agents receive child results and integrate them. Model-call concurrency slots are released before tool calls and waiting, so a parent does not occupy the slot a child needs to finish.

Agent communication also belongs to the harness, so it works across different providers. `send_message` targets another member of the same run, including siblings and parents. `read_messages` and `wait_message` let agents read or await correspondence. Delivery occurs at a model-turn boundary; an already running vendor inference is not secretly modified. Waiting releases the model slot. `followup_agent` resumes an eligible finished helper with a new assignment and preserved context under the same shared budget. The team correspondence is recorded separately from messages addressed to the user and exposed in the agent panel.

**The user writes to a working agent.** While a run works, the chat's message field sends to its root agent and the agent inspector to the selected agent, root or helper (`runtime:message` → `runtime.postUserMessage(runId, agentId, text)`, `mailbox.mts`). The message is a communication from the pseudo-participant `user` (`kind: 'message'`, `via: 'user'`, up to 20 000 characters) in the agent's mailbox, plus a trace `From the user: …` on the agent; it does not count against `maxMessages` and does not pass the router. It reaches the model at the next step, apart from the team's mail and whole, under `MESSAGE FROM THE USER` (the user's own words; they take precedence over the earlier plan): on the envelope transport at the top of the next prompt's mail block; on the session transport at the end of the agent's next Orbit tool result (marked read with `delivery: 'tool-result'`), else in the resume after its turn, since unread mail keeps an answer from being accepted. A waiting agent is woken, a finished helper works again (next generation, its result goes to its parent and the root), and the session system block and the MCP server's instructions tell the model that such messages are genuine. Both headings carry the recipient's secret mark, `[orbit:<mark>] MESSAGE FROM …` (`AgentRecord.mailMark`, ten hex digits, not in agent snapshots or events), and only the agent's own instructions (the session system block, which Codex gets as the thread's developer instructions, and every session's first prompt; the envelope prompt) name it: the same words in a file, a command's output or a helper's result, without the mark or with another, read as data. The mark lasts the agent's life, and a continuation that resumes the root's session after a restart keeps it: the run the restart ended saves the root's mark in `RestartMark.mailMark`. A message from an agent above the recipient in the team (its parent, the parent's parent, up to the root) steers it the same way: a session turn receives it whole under `MESSAGE FROM YOUR SUPERVISOR` (sender and message id) at the end of the next Orbit tool result instead of the unread count, and a prompt carries it the same way, after the user's block and ahead of the `TEAM CORRESPONDENCE` excerpts. Such steering mail does not wait for a long turn (`runtime/steer.mts`): when the turn makes no Orbit call within `ORBIT_STEER_GRACE_MS` (2 s), Orbit checks it every 250 ms and cuts it off at the first step boundary after the provider has spoken, when no native tool runs, no Orbit call is announced or in flight, no approval waits and the model's current step has only just begun: at most `ORBIT_STEER_STEP_MS` (3 s) since the last tool call ended or, before any, since the model's first event (text, reasoning or a tool; a CLI's stderr line or a note from before it started does not count) (`TurnWatch.stepAge`). A step the model is already thinking or writing is let finish, with one `steer` trace saying so: a cut would lose what it has thought and the repeat would think it over again (measured 2026-09-30: a flagship at max effort spent 134 s on one step, and two messages and a pause cut three such steps in a row, so it never answered). The message then goes out right after the step's tool call, or with the next turn when the step ends the turn. The cut turn is refunded and repeated at once with the note `INTERRUPTED FOR A MESSAGE`, in the same session (a first Claude turn resumes the session Orbit opened with `--session-id`; the other providers' first turns start fresh with the note). A resumed turn cut after its provider spoke is repeated with the new note only: its prompt is in the session, so its entries are not carried again (`PauseInterrupt.spoke`, `pause.interruptedSession`); before, every cut added another copy of the earlier notes. Mail between peers never cuts a turn. A finished run, an unknown, failed or stopped agent, a root that has already answered, an empty text and a helper in or past its last allowed turn are refused with the reason shown to the user.

**Pause, resume and stop.** The user holds any agent of a working run (`runtime:pause` / `runtime:resume` → `pauseAgent` / `resumeAgent`, `runtime/pause.mts`); helpers can also be stopped (`runtime:stop-agent` → `stopAgent`). A pause sets the agent's own `paused` flag and holds it and every descendant: `pausedBy` walks the parent chain. `providerTurn` waits at `pauseGate` (status `paused`, no model slot held) before it takes a slot, and gives the slot back if a pause arrived while it queued. `activeTurn.interrupt()` cuts every running turn of the subtree off at once: the turn's controller kills the CLI, and the turn throws `PauseInterrupt`, never a provider failure, so no failover follows. The envelope loop also waits at the gate before each tool call, and `dispatchMcp` refuses calls from a held agent. On resume the loops carry a `PAUSED BY THE USER` note: what the cut-off turn had streamed and which native actions it had started. The envelope transport keeps it in the transcript. The session transport resumes the same session with the note leading the prompt and rewinds `sessionCursor`, so helper results and the instruction the cut-off turn carried are sent again; the results of helpers that finished by then are collected before the repeat, and a wait the cut-off turn left behind took none of them (it ended with its turn, see Two transports). A session that cannot be resumed after the kill (`pausedSession`) is dropped once and replaced by a fresh one. Resuming clears only that agent's own flag: a helper paused on its own stays held. Stop marks the helper `stoppedByUser`, cancels its descendants and aborts its controller. The helper ends `cancelled` with an error telling the parent not to redo the work unless the user asks, and with its last logged actions as its result. The run stays `working` while agents are paused. During a turn the window gets the running action count (native plus Orbit tool calls in `turnTimings`) at most once a second (`publishProgress`), because a session turn can hold a whole task.

## Team traffic: router, file activity, project index

```text
agent A ──send_message / ask_team──▶ router ──▶ agent B (mailbox, next turn boundary)
   │                                   ▲
   └─ read/write ─▶ file activity ─────┘  who touched what → audience, notices, conflicts
```

The **router** (`router.mts`) is the single path for agent-to-agent messages. It is a deterministic dispatcher, not a model call: it costs no provider turn or slot and cannot start a conversation of its own. `ask_team` resolves the audience without ids: explicit `agentIds`, the author of `replyTo`, agents that changed (weight 10) or read (4) the named files or folders, agents whose name/task/touched files match the topic (score at least 3, at most three recipients, active agents first); with no match a worker's question escalates to its parent and the root gets an error. Every message, including plain `send_message`, passes `pass()`: an exact repeat to the same recipient is refused, and a pair that exchanged six messages without either side making progress (a successful write or edit, a delegation, a native file change or a command's attributed changes — `agent.workDone`) is closed until one of them does something. Saving a note or another message does not reopen it, so polite chatter cannot loop.

When an agent changes a file, the router posts a `notice` communication to every other *active* agent that read or changed it (finished agents are neither woken nor told). Notices from one writer to one reader coalesce while unread and are deduplicated per reader turn. Two writers on one file produce a conflict notice. Notices are information: they never count as messages for `maxMessages`, never wake a wait, and never keep an agent from finishing (`pendingMail` excludes them), so they cannot extend a run. Routing decisions are communications carrying `via: 'router'` and `route: { via, reasons }`, plus traces under the pseudo-participant `router`; the router is not in `agentNodes`, so no loop over agents (waiting for children, broadcasting, results) treats it as a worker.

**File activity** (`file-activity.mts`) records, per run, which agent read or changed which workspace path. Sources are Orbit's file tools (exact), provider events of native tools (Codex `file_change` `changes`, Claude `Read/Edit/Write` `input`; a native write counts only after a completed status, failed or declined ones are dropped) and files a `run_command` changed, attributed only when unambiguous (no overlapping command, no provider turn running, no other active chat in the folder, at most 40 files). It feeds each agent's public `files`, the FILE MAP in every turn's prompt, the `sharedWith` field of write results and the router.

The **project index** (`project-index.mts`) is a local, model-free index per workspace: path, size/mtime version, language, line count, up to 200 symbols with line numbers, imports (relative ones resolved into a dependency graph), a first-comment summary and the 60 most characteristic terms per file. Terms are stemmed the way memory notes are (`text-index.mts`: plural *s*, then five letters), and the words of the file's own symbols and first comment weigh three times a passing mention, so "refreshing indexes" reaches `refreshIndex` and a module is found by what it says about itself. File lists come from `git ls-files -co --exclude-standard` (run from a neutral working directory, because Windows locks a process's cwd; ignored bundles such as `Orbit-standalone-*` cost nothing because Git never lists them) or, when Git errors or lists nothing (a folder its parent repository ignores), a bounded walk that skips `node_modules`, build output and symlinks. Scans are incremental by size+mtime and deduplicated per workspace; an index loaded from disk is never considered fresh, and one written by an older analyzer version is rebuilt once. A path an agent touches that differs only in case from the listed one updates that entry on a case-insensitive disk. Content over 512 KB, generated and binary files are listed without content. Search is lexical over inverted lists of terms and of symbol words: path > symbol > IDF-weighted terms, one symbol hit per query word per file, and a test file ranks a little below the module it tests. The index file in `userData/project-index/` is a cache, written compact and without a backup copy: a damaged one costs one rescan. `index_search`/`index_outline` are read-only tools; the run starts a scan immediately and the first prompt waits for it for at most 2.5 s.

## Chat team memory

The UI's chat history contains only the root agent's words. At `start`, the runtime therefore collects the earlier runs of the same project and chat (in memory plus `RunStore.forChat`) and builds a digest for the root prompt: per earlier turn the request, the answer, each helper with task, result and touched files, and the latest team messages; the two newest turns in detail, older ones in one line, at most 6000 characters. Workers do not receive it. `team_history` returns the full reports within one observation's budget, and `spawn_agent { continueFrom }` seeds a new helper's "previous work" from an earlier agent. All of it comes from persisted run snapshots (agent `files` included), so it survives a restart. It is data the model must verify, not evidence that the files are still as they were.

## Subscription quotas and failover

```text
CLIs ──▶ quota.mts readers ──▶ QuotaMonitor (one per app) ──▶ window: "Квоты", chip, agent panel
             ▲   live events (Claude rate_limit_event, Codex rateLimits/updated)
runtime ── before each turn ──▶ assess(agent's provider, model) ──▶ near/exhausted? ──▶ failover.replacements ──▶ handover
   └────── on a refused turn ──▶ classifyQuotaError ──▶ markExhausted ──▶ handover, repeat the turn
```

**Readings** (`quota.mts`) come only from what a CLI itself reports; no OAuth token is read and no vendor HTTP API is called. Codex: the app-server request `account/rateLimits/read` (5-hour and weekly windows, plan, credits) and its rolling `account/rateLimits/updated` notifications. Claude Code: the text of `claude -p "/usage"`, a local command that neither calls a model nor spends quota (`num_turns: 0`), plus `rate_limit_event`s in the stream, whose `utilization` is a fraction of the window. Antigravity: the JSON of `agy -p "/usage"` (groups of models, each with a 5-hour and a weekly bucket). Cursor: `agent about` names the plan and nothing else. Ollama is unmetered and a custom endpoint publishes nothing. A snapshot is a list of windows `{ kind, usedPercent, resetsAt, scope, models }`; `models` limits a window to model-name fragments (Claude's per-model weekly limits, Antigravity's groups), so `assess(snapshot, { model })` counts only the windows that bind that model, and a window whose reset time has passed counts as empty. `QuotaMonitor` caches for a minute, shares one refresh among concurrent callers, retries a failed read after 20 s while keeping the last good figures marked stale, and keeps a *refusal mark* per provider: after a refusal the provider is out of rotation until the reset time the vendor's message named (30 minutes when it named none, ended early if a fresh reading is measurably below its limits).

**A refusal** is recognised by type where the provider gives one (Codex `usageLimitExceeded`/`rateLimitExceeded`, Claude's rejected `rate_limit_event`) and otherwise by wording (usage/5-hour/weekly limit, 429, quota, RESOURCE_EXHAUSTED, credits depleted …). Context-window overflows, cancellations and timeouts are never refusals.

**Handover.** Every provider turn is a fresh inference and the agent's memory lives in Orbit (transcript, work log, files, team directory, mailbox), so an agent may change model between two turns without losing anything: `agent.providerId/model/reasoningEffort` change and the next prompt is built for the newcomer. What is added is an explicit note (`failover.handoverNote`) pushed into the transcript and the work log: who is replaced and why, the state (turns, files written and read, teammates running and finished, unread mail), the last actions, and, when a turn was cut off, the text it had streamed and the native tool actions it had started (they may already have taken effect, so the newcomer is told to verify before repeating). An agent that has done nothing yet just starts on the new subscription. Handovers are recorded on the agent (`agent.handovers`, persisted with the run) and announced by an `agent.handover` event, a trace and, for the root agent, a chat notice. A turn the failover repeats does not count against `maxTurns`/`maxTotalTurns`. Each agent changes subscription at most eight times.

**Choosing the replacement** (`failover.replacements`, pure). Candidates are the models of connected providers (the health list) plus the user's pool; the agent itself, failed candidates, providers that just failed to answer at all (excluded for the whole run for ten minutes), local models and endpoints (unless pooled) and providers at or past the switch threshold are left out. After a refusal a second, relaxed pass accepts providers that are near but not over their limit. Quality is compared by tier (`model-tiers.json`: 3 flagship, 2 strong, 1 light, 0.5 weak, 0 unknown or unreliable): measured tiers from the model audit (`docs/MODEL-AUDIT.md`) come first, the rest follow naming conventions and place doubtful models low. A candidate needs the tier of the agent's model (its actual model; else, and for a tier-0 model, a deliberately high per-provider baseline), one lower if the run allows weaker models (so a flagship never gets a light one and a strong agent never a weak one), and unknown or unreliable models only from the pool, as are the models listed in `excluded` whatever their tier (Claude Fable, at the user's request). Order: pool first, then the closest tier (equal, better, weaker), then the most quota headroom. The reasoning level is kept only where the target offers it (Google models have none; Cursor encodes it in the model name; a pool entry's level wins). Settings (`quotaFailover`: on/off, switch point 50–99%, allow weaker) are taken per run; nothing happens without a `QuotaMonitor` (tests and embedders that do not pass one see the old behaviour).

**A new helper's model by kind of work** (`model-routing.mts`, pure; `runtime/handover.mts` `routeSpawn`). `spawn_agent` with `kind` (code, review, lookup, text) and no `model` takes the first candidate of that kind in `electron/model-routing.json` (ordered by the model audit) that the user's pool allows (the run's own provider always), that did not fail to answer a moment ago, that the health list shows connected and offering that model, and whose quota for that model is below the run's switch point. The quota readings are refreshed as for a handover; the health list is waited for at most 8 s, and without it only the parent's, the run's and the pool's providers count. `providerId` alone narrows the candidates to that subscription; an explicit `model` skips the routing. The audit's reasoning level applies only where the caller, the pool, the provider's settings or the parent's own model set none. The result (`routed`) and the delegation trace name the choice and the candidates passed over with the reason; without a usable candidate the helper gets what it would get without a kind. Only a call that will route waits: one refused for an ended run or parent, or reusing a helper by its name, returns at once, as does a `providerId` with no candidate of that kind; two calls for one name racing through the wait still create one helper. A pause that cuts the caller's session turn during the wait makes the call create nothing (`turn_interrupted`), since the model never sees its result.

Run limits cover total agents, nesting depth, simultaneous model requests, turns per agent, and total turns across a run. Context and observations are bounded. Reaching a limit produces an explicit failure or tool error. It never fabricates a completed review.

**Tokens per agent.** Every agent keeps the tokens it has used over its whole life (`agent.usage`: `inputTokens` with the cached part included, `cachedInputTokens`, `outputTokens`), live while a turn runs and public (events, snapshots, run history); the run's `usage` tokens are the sum of its agents and the directory (`list_agents`, the team directory of a prompt) shows `tokens` (input + output). The providers turn what a vendor reports into *growths*: a `usage` event carries the tokens spent since the previous one, and `runtime/turn.mts` `recordUsage` only adds them (one shape: Anthropic's and Cursor's cache counters are added to the input, OpenAI-style input already includes the cache), publishing at most once a second. What the vendors really report (checked against Claude Code 2.1.285 and codex-cli 0.155): **Claude** repeats one API call's figures on `message_start`, on every `assistant` event and on `message_delta`, and `output_tokens` is final only on `message_delta`, so the parser keeps the most it saw per message id; a `result` states only the agent's own calls of its stretch (never its native subagents', whose calls the stream shows on `assistant` events with a stale output) and can follow the next stretch's calls, so results are summed and only the shortfall against the calls seen is added. **Codex** counts per thread, never per turn: `turn.completed` of `exec` carries the thread's running total (with `exec resume` too), and the App Server's `turn/completed` has no usage at all; its `thread/tokenUsage/updated` carries `total` and `last` and is replayed right after `thread/resume`. `codex-usage.mts` keeps the last total per thread and counts the difference; a notification of a turn the process did not start (the replay) only sets the start, and a thread resumed in a process that never saw it (after an Orbit restart, `exec resume` only) leaves that one turn uncounted instead of charging the agent for earlier work.

## Working memory and the loop guard

On the envelope transport every provider turn is a fresh inference: the prompt Orbit assembles is the agent's only memory. It has three parts. Fixed instructions and the compact shared context come first (stable prefix). A `WORK LOG` follows: one line per call the agent has executed (tool, target, outcome), kept for the life of the agent and bounded to the newest 60 entries plus a tally of older ones. The rolling transcript comes last and holds full observations. The transcript never drops below a floor (40 000 characters, 9 000 for Ollama/compatible endpoints) whatever the fixed part costs, so a requested `maxContextChars` that cannot hold the instructions plus a usable window is raised rather than spent on starving the history. When old entries scroll out, the log still records what they were. The transcript's size is tracked per entry as it grows, so trimming compares numbers instead of re-serialising the whole transcript after every observation. On the session transport the provider keeps the conversation itself; Orbit keeps the same ledger, work log and transcript (MCP observations included) for the handover note, the inspector, a fresh session after a handover and a switch to the envelope loop, but sends a resumed session only what is new.

A loop guard runs after every envelope tool turn. A call is a *repeat* when the same tool and arguments return the same result, compared after removing self-changing fields (turn counters, timestamps) and timings in output. A turn is *stale* when every call in it is a repeat; waits that really blocked are not counted. Two stale turns in a row add a directive to the transcript, four stop the agent with a partial result that lists its last actions and helpers' results, and its still-running descendants are cancelled. Any novel call resets the counter, so this is not a turn limit and long varied work is unaffected. Independently, eight consecutive turns that changed nothing (no write, delegation, message or saved note) add a nudge to conclude, and a harness reminder (`model_evaluate`, improvement mode) that the model ignores three times in a row is dropped. A *poll budget* catches what the loop guard cannot see because each answer differs: six consecutive envelope turns made only of `list_agents`, `read_messages`, `context_read` or waits add one nudge (per streak) to call `wait_agent` or `wait_message` once with a timeout instead; nothing is stopped for it. On the session transport the model's native loop owns tool repetition; the loop guard and the poll budget do not apply there.

## Endless improvement loop

With the improvement switch on (`settings.improvementMode`), a message the user sends starts the chat's loop. Every step of the loop is one run that takes a batch of the plan's tasks (up to about four independent ones, run in parallel by isolated helpers), so each batch starts with a fresh model context instead of one conversation that grows for as long as the loop runs, and the batch costs one restart of Orbit instead of one per task. The loop works in any project's chat: it changes that project, or Orbit itself (see *restart_orbit from any project* below).

**Renderer** (`src/improvement-loop.ts` decides, `src/useOrbitState.ts` acts). The loop lives on the chat (`ChatThread.loop`: goal, task number, failures, the next retry, the last handled run, the closed plan tasks as `id|title` keys with `|blocked` added for a blocked task, so a blocked task done later counts as closed) and is saved with it, so it survives reloads and restarts. A driver effect looks at every chat with an active loop in every project. Once the chat's latest run has ended (nothing running, no start pending, no restart continuation awaited), it handles that run once: a completion that closed a new plan task starts the next task at once; a completion that closed nothing, a failure, an interruption, a cancel the user did not ask for (Orbit quit, the runtime restarted from Settings) or a restart that brought no continuation is retried after 1, 3, 10, then 30 minutes; a plan left `blocked` pauses the loop until the user writes. The user's Stop ends the loop directly, before it cancels the run. A loop task is a new run in the same chat with `history: []`, `improvementMode: true`, `loopTask: N` and a generated prompt (the goal, the user's later messages in the chat, the previous outcome when it was not a normal completion). The chat shows a `kind: 'loop'` note for it instead of a user message, and a banner with the task number, its state and «Остановить цикл» / «Запустить сейчас». A start whose run never appears within 60 s (a reload swallowed it) is repeated. A start the runtime refuses because Orbit is busy (`START_REFUSALS` of `electron/runtime/lifecycle.mts`: the chat's previous run is still ending its processes, another chat's restart is being applied, a process cleanup in the project) is repeated after 5, 10, then every 30 seconds without a note and the banner says it waits; any other refused start backs off 1, 3, 10, 30 minutes on its own count with a warning. Neither is a failed run, so the next prompt still reports how the previous run really ended, and both counts end once a started run is handled. Turning the switch off stops every loop (a working task finishes). One loop in all of Orbit is active at a time: a second one would keep a chat working almost always, and `restart_orbit` refuses while other chats work.

**Runtime** (`electron/runtime/improvement.mts`). An improvement-mode run takes the plan and the handoff from the newest earlier run of its chat that has one (live runs and `runStore.forChat`); the status is reset to `implementing` or `planning` (only a restart continuation keeps the status of the run it continues, so a pause set before `restart_orbit` survives it), and the tasks already closed are recorded as the run's baseline. `improvement_plan` accepts `handoff` (at most 2 000 characters: what the next task's fresh context must know), keeps unfinished tasks, clips titles and evidence and keeps the 30 newest done tasks. A task of the baseline that is still closed keeps its title (the result lists it in `keptTitles`), and a clipped copy of its evidence from the progress block is replaced by the full text. `blocked` needs a blocker documented in this run: a new blocked task, a task blocked now, or new evidence for an earlier blocked one (a continuation may keep its inherited blocker). The root sees a bounded `CURRENT IMPROVEMENT PROGRESS` block (counts, open tasks, the last eight done, the handoff) and the loop rules: one batch per run (the `working` tasks first, then up to about four independent pending ones, each worked on by its own isolated helper: `spawn_agent {kind:'code', isolation:'worktree'}`, or `isolation:'orbit'` for a change to Orbit's own code from another project's chat; the helpers start within the first minutes and the root does independent work while they or a reviewer run instead of waiting); close every task with `improvement_plan` as soon as it is verified, with targeted tests for the new logic only; call `restart_orbit` once, as the last step for the whole batch, when Orbit's own code changed (it runs the full checks and the build itself, so no full suite and no mutation runs beforehand); a bounded goal that is fully reached sets the plan `blocked` ("goal reached: …"). The root's answer is accepted only when:
- no task is left `working`;
- at least one task was closed in this run (any number may be: a batch): a closed task that is new, or whose status changed (blocked before, done now). A restart continuation and a run that sets the plan `blocked` are exempt; marking the inherited plan `completed` again or renaming an old done task is not;
- when Orbit's own code changed, `restart_orbit` succeeded, or was refused in a way the next restart resolves (cycle limit, other chats working, declined). "Changed" is the code on disk against the code the running Orbit runs (`restartHost.unapplied()`: a helper's merge, a shell command or git count too); when that cannot be told (no health report), the files the run wrote decide only in a run on Orbit's repository. In another project's chat those are the project's files, which no restart applies, so nothing is asked there unless Orbit's code on disk differs.

Otherwise the root gets a specific reminder, three at most, and then the answer is accepted with a note naming what is missing. The snapshot and `run.started` carry `loopTask` and `improvementHandoff`, and `run.started` also carries the loaded plan. A batch restarts Orbit once, but when batches are short the self-upgrade cycle limit (`ORBIT_UPGRADE_MAX_CYCLES`, 3 per 30 minutes) can still refuse a restart: the tasks stay done, and the next batch's restart installs both changes.

## Attribution, persistence and cancellation

`start` accepts `projectId`, `chatId`, `workspace`, `prompt`, `history`, `providerId`, optional `model`, access policy, memory setting and limits. Events contain `runId`, `projectId` and `chatId` even when the renderer is displaying another chat.

Canonical events: `run.started`, `run.info`, `agent.created`, `agent.updated`, `agent.handover`, `trace.added`, `message.streaming`, `message.added`, `communication.added`, `change.added`, `run.finished`, `run.failed`, `run.cancelled`. A run that an Orbit restart ended finishes with `run.finished` carrying `status: 'restarting'` and `restart { reason, requestedAt, source, note }`; the `run.started` of its continuation carries `resumedFrom` and `resumeChain`. Listeners receive one detached copy of each event (never live runtime state). Snapshots contain agents, traces (the newest 2 000), messages, execution settings and timestamps; while a run is active its file is rewritten at most once a second for a burst of events, the terminal event is written at once. The renderer associates root answers with the owning chat and subagent output with the inspector. Updates to a communication reuse its ID, so delivery updates do not duplicate messages.

Communication events and the snapshot's `communications` array retain sender, recipient, content, time and delivery state. Messages cannot cross into another run or project merely by naming an agent. The UI restores correspondence alongside the agent tree after a reload.

The runtime lives in its own process (see *Process model and restarts*), independent of the displayed chat. Durable snapshots survive renderer reloads, runtime restarts and app restarts. Cancellation propagates through one run to its children and provider process trees. A restart marks previously active snapshots `interrupted`; saved history can be used in a new turn. The exception is the run whose agent asked for the restart: it ends with the terminal status `restarting`, which the run store keeps on load, and a new run in its chat continues it. This is not a daemon that survives closing Electron.

## Process model and restarts

```text
Electron main (the shell)                              runtime process ("Orbit runtime", utilityProcess)
  window, preload, IPC guard, dialogs, shell             runtime-child.cjs → runtime-host.mts createRuntimeService
  health reports, relaunch, restart signals              OrbitRuntime, every store, QuotaMonitor, Orbit MCP server,
  8 channels of its own (ipc-handlers.cjs)               provider CLIs, the restart host; 26 channels (runtime-api.mts)
  runtime-client.cjs  ◀──── runtime-protocol.mts ────▶  runtime-child.cjs
```

**Who runs where.** Run from the repository, main is only the shell. It loads `SHELL_FILES` of `electron/fingerprint.cjs` (`main.cjs`, `preload.cjs`, `ipc-contract.cjs`, `ipc-handlers.cjs`, `ipc-guard.cjs`, `runtime-client.cjs`, `fingerprint.cjs`, `git.mts`, `runtime-protocol.mts`, `skill-files.mts`, `window-proxy.cjs`; the list also counts `package.json`) and nothing else under `electron/`: `tests/main-load.test.cjs` fails when it does, or when one of those ES modules imports another `electron/` module at run time. `window-proxy.cjs` gives the window's session the proxy of `HTTPS_PROXY`/`HTTP_PROXY` while the system's settings send every host of the YouTube player directly (Chromium reads only the system's; a PAC route for any of them keeps the window on the system's); the runtime's `resolve-proxy` is answered from a separate in-memory session (`orbit-system-proxy`) that stays on the system's settings. `OrbitRuntime`, the stores (memory, project context, skills, project index, run history, window state), the `QuotaMonitor`, the Orbit MCP server, the provider CLIs and the restart host live in a child process that main forks with Electron's `utilityProcess` (`ORBIT_RUNTIME_MODE=child`, the default from the repository). `ORBIT_RUNTIME_MODE=inprocess` builds the same service inside main behind the same client interface, without a runtime restart; a packaged build defaults to it, because forking an entry inside `app.asar` with `utilityProcess` is not verified. Main answers eight channels itself (`workspace:pick`, `workspace:inspect`, `workspace:clone`, `shell:open`, `app:ping`, `app:relaunch`, `runtime:restart`, `runtime:status`) and forwards the other 26 channels of the IPC contract (`RUNTIME_CHANNELS`) with the window's arguments unchanged; `SHELL_CHANNELS` and `RUNTIME_CHANNELS` together are exactly the contract (`tests/main-load.test.cjs`). The runtime's events (`runtime:event`, `quota:update`, `restart:notice`) are passed on to the window; the client's own state goes out on `runtime:status-changed`.

**Protocol** (`runtime-protocol.mts`, `PROTOCOL_VERSION = 3`; it imports nothing). Main → runtime: `call`, `approval-result`, `renderer-healthy`, `shutdown { mode: 'quit' | 'restart' }`, `proxy-result`. Runtime → main: `ready { pid, ms, protocol }`, `result`, `event`, `approval`, `approval-cancel`, `shutdown-done { marked }`, `log`, `fatal`, `uncaught { error, count }` (an error nothing caught after `ready`: the first at once, then at most one a second with the number of errors behind it), `processes` (`{ pid, startedAt }` of every process the runtime started that still runs, the time taken right before the spawn; it replaced the bare `pids` of version 2), `resolve-proxy`. Messages are plain structured-clone data: never a function, an `AbortSignal` or a class instance, and an error crosses as `{ message, stack?, code? }`. A message that does not parse is logged and ignored, except an approval that carries an id, which is answered no; the runtime normalises the approval fields it sends (`toolUseId` only when it is text). A runtime whose `ready` names another protocol version is refused, since only a full relaunch loads both sides from the same code. Tests fork the same entry with Node's `child_process.fork` and `serialization: 'advanced'` (Node 22, `--experimental-strip-types`).

**The client** (`runtime-client.cjs`). Calls made while the runtime starts or restarts wait in a queue for at most 30 s; a start that does not report `ready` within 20 s is killed. Calls in flight when a restart ends the old process fail, except the repeatable ones (reads and `state:save`), which the new runtime answers first. A runtime that fails before `ready` (a `fatal`, an exit, the start timeout, another protocol version, a fork main refused) leaves the state `stopped` with its error and is not started again on its own: the same code would fail the same way, and a retry would race the self-upgrade watcher restoring `electron/`. One that crashes after `ready` sets `crashed` with `retrying: true`, rejects the pending calls and is started again after 250 ms, once what it left running has been stopped (5 s at most), at most three times a minute; the next crash leaves it `stopped` until a restart by hand. `RuntimeStatus` (`runtime:status`, pushed on `runtime:status-changed`) is `{ state, mode, pid, since, lastRestartMs, restarts, retrying, error?, lastError? }`; `lastError { message, at, count }` follows the `uncaught` reports of the process that runs now. A call, a restart or a start that a quit or a relaunch ends fails with the code `ORBIT_SHUTTING_DOWN`, which main does not report as a failed start or restart. Approvals are bridged: the runtime sends the question, main shows one dialog at a time, and the dialog's signal aborts when the runtime withdraws the question (the run stopped) or its process exits. After the runtime exits, main reads the Windows process table once (PowerShell `Get-CimInstance Win32_Process`, 0.4–0.75 s measured) and stops only verified leftovers: a recorded process that still runs with a creation time matching its recorded start (100 ms before to 2 s after), and children of a recorded process that is gone, created after its start and before the runtime's exit (or before another process took its pid); never main, the runtime, or the pids 0 and 4. On Windows the runtime's direct children die with it (libuv's kill-on-close job) but their own children do not, and `taskkill /t` cannot reach those through a parent that is gone; elsewhere the table is not read and nothing is stopped. The Electron `session` exists only in main, so the runtime asks main for the system proxy of Antigravity's endpoint (`resolve-proxy`; no answer within 3 s falls back to the registry).

**The runtime process** (`runtime-child.cjs`) builds the service for the profile and the repository main names in `ORBIT_USER_DATA_DIR` and `ORBIT_REPO_ROOT` (`--user-data` and `--repo-root` win over them); it reads those two and `ORBIT_PARENT_PID` once and deletes them, so the processes it starts do not inherit them. It posts `ready`, serves calls and exits after `shutdown-done`. Under a `child_process.fork` parent (tests, a Node host) it also shuts down on its own when the IPC channel disconnects or a 1 s watchdog finds the parent gone; under `utilityProcess` Chromium ends it together with main (within about 50 ms, measured), so a crash of main stops no run and saves nothing beyond what was already written. A failure before `ready` is `fatal` and exit code 1; after `ready` an uncaught error is reported as `uncaught` and the runs go on. A shutdown runs once: for `restart` the run named by the intent (below) is marked `restarting` first; every other active run is stopped; the MCP server and the stopped runs' operations get at most 2 s; open approvals are withdrawn; pending run files are written and run history, project index, memory and skills are flushed. With `ORBIT_SMOKE=1` the service refuses to start unless `ORBIT_RUNTIME_FIXTURES` supplies all three fixtures (`runProvider`, `inspectProviders`, `patchQuotaReaders`), so a smoke never reaches a real CLI or subscription.

**Restart levels.** `full` (`--relaunch`, `app:relaunch`): the runtime shuts down for a restart, then `app.relaunch()`. `runtime` (`--restart-runtime`, `runtime:restart`, Settings → Runtime): it first waits for the start of Orbit to be reported (`runtime:restart` for at most 60 s, then it answers that Orbit is still starting), and it is refused when the shell files on disk differ from those main loaded ("shell files changed — relaunch Orbit", with a failed report of that generation for whoever waits for one); the same check refuses the fork of an automatic restart after a crash, which then leaves the runtime stopped. Otherwise the old process shuts down for a restart (5 s, then its tree is killed), a new one is forked with the code on disk, the window must pass its health check again (one reload allowed), and the healthy report is written only if that very process is still ready then; a request that arrives during a runtime restart gets one more restart after it. In `inprocess` mode the signal relaunches the app, `runtime:restart` answers an error and the Settings button is disabled. `renderer` (`--reload-renderer`): every window reloads the build on disk; the runtime is not touched. A second instance started with one of the flags delivers it through `second-instance` and quits. A start or a runtime restart that a quit or a relaunch cuts short writes no report.

**Health generations.** Every start, runtime restart and renderer reload is a generation with exactly one report in `artifacts/self-upgrade-health.json` (`ORBIT_HEALTH_FILE` overrides the path, a relative one from the repository, `0` disables the file; `scripts/self-upgrade.cjs` and the runtime read it by the same rule, and without a file the script restarts nothing); the first result of a generation wins. The report carries `level`, `generation`, `restartedAt`, `shellHash`, `runtimeHash` (the code the shell and the current runtime loaded), `rendererHash` and `rendererSource` (the renderer inputs the window runs: from the build record of the `dist/` it loaded, `build`, else hashed from disk, `files`) and `runtime { mode, ready, pid, ms }`. The start's report needs the renderer check (a preload round trip and a mounted UI) and a ready runtime; a runtime restart's report needs a ready runtime and the window checked again. A healthy full or runtime report is sent to the runtime as `renderer-healthy`. After every healthy report, a renderer reload's included, main starts `scripts/self-upgrade.cjs --record-running … --renderer-hash …` detached (repository runs only), which records the running sources as the rollback base.

**restart_orbit, continuation and rollback.**

```text
root agent ── restart_orbit {reason, continueWith, verify} ──▶ runtime/restart.mts: root only, write access, a run in
  any project's chat, not ORBIT_DEV, no other chat running (checked again after an Ask approval)
  └─ restart host (resume.mts) runs node scripts/self-upgrade.cjs [--no-verify] --reason … --continue-with …
       with ORBIT_RUN_ID/CHAT_ID/PROJECT_ID/AGENT_ID, ORBIT_RESUME_FILE, ORBIT_USER_DATA, ORBIT_RESTART_SOURCE=tool;
       output → one trace; meanwhile runtime:start in other chats is refused
     checks → build if the renderer inputs changed → level from fingerprints vs the running instance's health
       failed check, cycle limit, lock    → tool error with status, exit code, the last 80 lines; nothing restarts
       none                               → "nothing to apply"
       renderer                           → --reload-renderer, health → tool result ok; the run goes on
       runtime / full                     → detached watcher: pending-resume.json written, then the signal
         old runtime shutdown('restart'): the named run ends `restarting` with its restart note and the intent's id,
           the tool call ends at once, other runs are stopped
         new runtime ready, window healthy → health report → watcher: verdict `relaunched`
           (failure → rollback per level, intent outcome `rolled-back` + error + patch before the old code starts;
            a watcher that fails itself → verdict `failed`)
         main → renderer-healthy → resumePending: wait ≤ 30 s for the verdict → checks → delete the intent
           → runtime.start(startPayload of the old run + continuation prompt, resumedFrom, resumeChain)
           → restart:notice to the window
```

The runtime never writes `pending-resume.json` (version 1; the script writes it atomically right before the signal, the watcher adds its verdict). `resumePending` runs once per runtime, at its first healthy report. Without a verdict an intent younger than 10 minutes is still continued after the wait. Nothing is continued after a rollback or a `failed` verdict, for an intent older than 30 minutes, when this restart would make `ORBIT_UPGRADE_MAX_CYCLES` in a row (default 3: the third is not continued), for a missing run or `startPayload`, for a run that finished on its own or that the user had stopped, when the run's `restart.intentId` is not this intent's id (a forged or stale intent; an `interrupted` run carries none), or when the run already has a continuation; each case is a `restart:notice` (`resumed`, `rolled-back`, `loop-limit`, `expired`, `failed`, Russian text) that the window keeps as a chat message of kind `restart`. The intent is removed before the continuation starts (a failed delete is retried, then the file is renamed to `pending-resume.json.consumed`; if neither works nothing is started), so a continuation that crashes Orbit is never started twice. Every run saves `startPayload` (its start payload without the prompt and the history). The continuation's prompt names the code that runs: «коммит <head> + незакоммиченные изменения, снимок <candidate>». Its root starts with the restart note in its transcript (the old root's work log, files, helpers, a turn the restart cut off, and the instruction to check the real state before repeating a write or a command); when it keeps the old root's provider on the session transport, its first turn resumes the old session with the continuation's message (for Claude also when `restart_orbit` came in the root's first turn: the session id of its last `turnTimings` entry), and a resume that fails drops the session id once and starts fresh (`runtime/loops.mts`). In the window, a chat whose latest run ended `restarting` without a continuation or a notice yet is busy for up to 2 minutes: no send, no delete. A second `restart_orbit` from the same run joins the script in flight, one from another run gets `busy`. A user's stop writes `artifacts/self-upgrade-cancel.json`, kills the script's process tree and removes the lock of the killed script; the script (at step boundaries) and its detached watcher (before the intent and before the signal) end with `cancelled` on a marker newer than their start, and a new request clears an old marker only when no live lock holder with a fresh heartbeat exists. The root agent's commands and CLIs get the same `ORBIT_*` variables (and `ORBIT_USER_DATA`) exactly where `restart_orbit` is offered, so its own `npm run self-upgrade` leaves the same intent (source `script`). An Orbit that the watcher starts inherits them from the agent's command, so `main.cjs` deletes them from its own environment at start.

**restart_orbit from any project.** Orbit improves itself from every chat, not only from one whose workspace is its repository. `restartOffered` asks for the root, write access, a restart host (Orbit runs from its repository) and no Vite dev server; the run's folder does not matter, and `onOrbitRepository` / `runOnOrbitRepository` only decide the wording. Nothing in the restart depends on the workspace: the script is `scripts/self-upgrade.cjs` of `host.repoRoot` (its `cwd` and its own `__dirname`), the intent names the run, chat and project through `ORBIT_*`, and the continuation starts from the run's saved `startPayload`, so it is a new run in the same chat, project and folder (the window keys notices, waits and the loop by `projectId`/`chatId`, never by a repository). The root of a run on another project gets, next to the tool's guide, a `YOUR OWN CODE` block: where Orbit's repository is, that a change goes through an isolated helper (`spawn_agent {isolation:'orbit', kind:'code'}`: a copy of that repository, merged into it when the helper finishes) or, with full access only, an edit of the repository itself, that `restart_orbit` applies it and the chat continues, and that skills it installs serve the project (`scope: 'project'`) or every project (`scope: 'global'`; the scope guard still keeps a skill that names the project in the project). Helpers never get the tool or the block. Changes to the project's own files are never applied by a restart; the work on the project and on Orbit stays apart.

## Memory tiers, retrieval and skills

```text
chat     working notes of one task thread ──promoted when used again──▶ project
project  verified knowledge of one codebase ──the same note, word for word, in ≥2 projects──▶ global
global   what holds in every project: preferences, how-tos, model assessments
skills   procedures worked out in a task: per project or global, with a track record
```

**Tiers.** All notes live in `memory.json`; an entry's `scope` (`chat`, `project`, `global`), workspace (canonical path, case-folded on Windows) and chat id decide who can see it. A run sees its chat's notes, its project's notes and, when allowed, the global tier. Workers default to `memoryProfile: 'project'` (chat and project tiers); `project-global` adds the global tier. A project can switch shared memory off: it then neither reads nor writes the global tier (notes *and* skills), and its notes never contribute to sharing. Legacy records without a workspace stay on disk, invisible. Common token strings are redacted before anything is stored. The chat tier has two halves: the notes described here (what was decided or constrained, written by agents or by the user) and the digest of earlier turns described under *Chat team memory* (what the team did, derived from saved run snapshots, never stored as notes).

**Bounded growth.** Each tier has a cap (chat 40, project 250, global 200; skills 60 per project and 100 shared), and a note is cut to 1 500 (chat) or 4 000 characters when an agent saves it (the agent is told when that happens); a skill an agent saves is cut to 12 000. Every entry has a *value*: confidence, recency (half-life 7 days for chat notes, 120 for project, 365 for global; twice as long for decisions and preferences) and use (`uses`, logged once per run and only when a note really matched the task or was read on purpose, so unrelated fill-ins cannot keep themselves alive). Over the cap the least valuable entries go first, the oldest among equals. The user's own notes (and the notes an older version saved from the UI, recognisable by their confidence of 100) and pinned notes are protected: never evicted, merged away or promoted, and an agent can neither overwrite nor remove them (`memory_save` with their id is refused; a near-duplicate is reported as already known). Model assessments are the harness's own records: agents cannot overwrite or remove them either, but they are capped (60, newest kept) and are never merged. An agent's note that says what an existing note says (title overlap ≥ 0.5 and text overlap ≥ 0.65, Jaccard over stems) updates it instead of adding a copy. After every finished run `maintain()` runs without a model: chat notes older than 30 days expire, chat notes that were used twice (preferences: three times) and have confidence of at least 70 are promoted to the project, near-duplicates (≥ 0.8) merge, low-confidence entries nobody used age out, caps are enforced. Deleting a chat deletes its notes without promoting anything. Usage counters are written lazily (a few seconds after the change, and on quit); every structural change is written to disk before it becomes visible, so a failed write leaves the state as it was.

**Isolation.** Isolation is enforced by the harness, not left to the model's choice of scope. A request to save something *global* (a note, a skill) is checked by `scope-guard.mts`: the text must not contain the workspace's absolute path (as given, resolved, or in its long/short Windows form), its folder name (three characters or more, unless generic like `src` or `lib`), a relative path that exists in it (however written: `src/a.js`, `./src/a.js`, `@/src/a.js`, non-ASCII names; a path with a space in a segment is not recognised), or its git remote (`github.com/owner/repo` or the bare `owner/repo`, found in the repository above the workspace and behind a linked worktree's pointer file). The checks lean towards raising the alarm: if any of them fires, the note is saved to the project instead and the agent is told why. A worker with project-only memory, or a project with shared memory off, cannot write global memory, and its global skills are kept in the project. Model assessments and skill pitfalls stored globally are scrubbed of the workspace path, of files that exist in it, of its folder name and of its repository; a pitfall recorded in a project skill loses the absolute path at once and never travels to a shared skill if it named anything of the project. A shared skill records the projects that used it only as short hashes. The guard is a safety net, not a judge of meaning: a note that describes a project without naming any of the above still depends on the model choosing the right scope, which is why sharing by promotion is so strict.

**Sharing by promotion.** Only the same note, word for word (identical set of words, numbers included; order and case ignored), found in at least two projects, of type pattern, fact or preference, not written by the user, passing the guard for each project, moves to the global tier: "port 3000" and "port 8080", or npm and pnpm, are different notes however similar they read. It looks across all projects, so it runs when the first run after start-up finishes and then at most every six hours, and only projects the UI has reported as sharing take part (the renderer reports each project's switch when it changes and at start-up; a project nothing has reported is treated as not sharing; start-up housekeeping never shares). Project copies stay, but are hidden from prompts while the shared note is visible. In practice this catches notes that agents reproduce identically; the main route to global knowledge is an agent choosing the global scope, under the guard.

**Retrieval.** `text-index.mts` is a small in-process inverted index (BM25; title ×3; stems: plural *s* removed, then the first five letters, so *memories*/*memory* and *проекты*/*проекте* meet; identifiers split at camelCase and separators). It is derived data, rebuilt at load and updated per change. Each model turn builds the memory block from `recall()`: pinned entries first, then matches for the agent's task, then the most valuable of the rest, per tier, within 4 500 characters (chat 25 %, project 45 %, global 30 %, unused room flows on). The orchestrator always sees the six newest model assessments. What did not fit is listed by short id and title, with how many entries are stored in all, so the agent knows it exists; `memory_search` reads it in full. Tools: `memory_search`, `memory_save` (scope `chat`, `project` or `global`), `memory_forget`.

**Skills.** A skill (`capabilities.json`) is a versioned, self-contained procedure: name, description, `whenToUse`, instructions; the previous ten revisions are kept and restore creates a new version. On top of the text it carries a track record: `uses` (once per run), `successes`, `failures` (`worked`/`partial`/`failed` via `capability_feedback`), the pitfalls reported with failures, and the projects that used it. The prompt lists the skills that match the task (ranked by relevance, then reliability `(successes+1)/(successes+failures+2)`), a few proven ones, and how many more exist; `capability_search` finds the rest and `capability_read` loads one whole, however long, and counts the use. Agents are told to check skills before improvising a multi-step procedure. Learning is prompted once per run, at the moment the root agent would give its final answer: when the run took ten or more provider turns without saving a skill, or a skill was loaded and not rated, the draft answer is kept in the transcript and the root gets one reminder to rate those skills and save a new one if it worked out something reusable, then to confirm its answer. It is a nudge, not a requirement: an answer without a save is accepted, and if that extra turn fails or comes back empty the draft is delivered. It costs one model turn; `skillLearning: false` in the start payload (Settings → "Учиться на задачах") turns it off, and so does disabling memory. A skill that says what an existing one says (name overlap ≥ 0.66 and text overlap ≥ 0.7) improves it as a new version instead of duplicating (the agent is told which skill it changed); procedures that merely share words are separate skills. A skill the user wrote stays protected when an agent improves it, and an agent's claim to be the user, the harness or the promotion pass is ignored. Maintenance drops skills nobody used for 180 days and skills that keep failing (three failures, reliability under 0.25), enforces the caps and shares, under the same word-for-word rule as notes, a procedure that was worked out independently in several projects, used at least once and tied to none of them. Skills are independent of the *memory enabled* setting (which no UI control turns off); the shared-memory switch of a project does apply to them.

**Skills as add-ons (packages).** A skill is any add-on Orbit builds for itself, not only a procedure: besides the text it may carry a package of files (pages, scripts, assets; `<userData>/skills/<package id>/`, `electron/skill-files.mts` keeps every path inside it, `electron/skill-packages.mts` validates and writes) and three generic mechanisms: `params` (typed values the user sets in the Skills panel, `capabilities:params`; an update by an agent keeps the user's value of a parameter whose key and type stay), `triggers` (today `task-completed` → `show` one of the package's `.html` files) and `commands` (named shell commands an agent runs in the package folder with its ordinary, approved tools). `capability_install` takes `files`, `removeFiles`, `fromDir` (a folder, for an agent inside the project or the temp folder, whose `skill.json` fills the fields the call omits), `params`, `triggers` and `commands`; it validates everything before it writes and puts the files back if the commit fails. `capability_read` returns `package.dir`, files, params with their values, triggers and commands, and refuses a switched-off skill. A skill with files, triggers or commands is protected like a pinned one (never expired, evicted or merged); prompt suggestions skip skills that only have a trigger. Revisions keep the text; the package is current state. Nothing in a skill runs by itself in the runtime: a trigger only makes the window show a page. Main serves `orbit-skill://<package id>/<file>` (a standard, secure scheme registered before the app is ready, read-only, 404 outside a package) with a Content-Security-Policy that allows the package itself, inline code, data:/blob: media and the YouTube player frame and no other host, and it keeps a skill frame from navigating outside its package (`will-frame-navigate`), so a page an agent wrote cannot send what it read anywhere; and `src/SkillStage.tsx` shows the page of each enabled skill with a `task-completed` trigger when a run of its project completes (after a `restart_orbit` restart, when the continuation completes; completions missed while the window reloaded are caught up once), one page at a time, full screen, in an iframe sandboxed to scripts and its own origin, with the parameter values in the address. The page closes itself with `parent.postMessage({ type: 'orbit-skill:close' }, '*')`; the stage also closes on Esc, its × button and after 10 minutes. A skill page that embeds YouTube gets a web Referer from main (`allowVideoEmbeds`), without which the player refuses to play. The first such skill is the celebration in `skills/task-completed-celebration/`.

**Attachments.** The composer attaches documents and images (the paperclip, drag and drop, paste). The window sends them as base64 to `attachments:save`; the runtime (`electron/attachments.mts`) writes them under `<userData>/attachments/<chat>/` (at most 10 files of 20 MB, 50 MB per message) and answers `{id, name, type, size, path}`. `runtime:start` and `runtime:message` accept attachments only inside that folder (`trustedAttachments`: name, type and size come from the disk). The root's task and a steering message list them as `ATTACHMENTS FROM THE USER`, one absolute path per line; the model reads them with its file tools (Claude sees an image it reads). Claude gets `--add-dir <userData>/attachments`, so the folder is readable in every access mode. The chat shows image thumbnails through `attachments:image` and opens a file through `shell:open-path`, which main allows only inside the attachments and skills folders. Until `attachments:save` answers, the message shows the chosen files without a path (nothing to open). `attachments:discard` deletes what no message will carry: the saved copies of a send or a message the runtime refused (the files go back to the composer), or a deleted chat's whole folder; only files `saveAttachments` wrote in that chat's folder can go, and a link inside is removed, not followed. A chat folder the deletion cannot remove at once (Windows refuses to delete a file another program holds open) keeps a mark `<chat>.discard` next to it (written before the folder is tried); `sweepDiscarded` deletes the marked folders when the runtime host starts and at every later chat deletion, after that chat's own folder (a mark is a file named after a folder `safeFolder` could give). A run keeps the files attached in it (its first message and messages to its agents, the newest `MAX_RUN_FILES` = 20) as `attachments` in its record; the continuation after `restart_orbit` gets those still in the folder (`resumeAttachments`, checked by `trustedAttachments`), its restart note lists them for a root that starts fresh, and it keeps them for the next restart. In the chat history sent with a new task, a message's paths (`attachmentNote`) come before its text, so that the bound of an entry (8000 characters, less in the prompt) cuts the text, not the paths.

**Shared project notes.** `context_save` notes remain the project's code-knowledge cache with dependency hashes (see above); `project-context.json` holds per workspace only the notes (the Git fingerprint and folder counts an older version stored beside them are dropped on load), and what agents receive is the notes with their staleness plus the folder overview. The notes agents leave automatically (`agent:<chat>:<name>`, `progress:<chat>`) are working state of a chat that happens to live in the project's file, so they are budgeted per chat: 30 per chat, the four most recently active chats, 14 days. A busy chat cannot push out another chat's notes, and notes saved on purpose are never touched.

Atomic JSON writes and backup recovery are shared by state stores. Run snapshots are batched during activity and flushed at completion/shutdown. `RunStore` holds and lists the newest 200 runs (the run list, `forChat` for the chat digest and the improvement plan); an older file stays readable by id until there are more than 500 run files. Then `prune` deletes the oldest by last write, each with its `.bak` copy, leftover temporary files and `images/<run>/`, the run file last so a locked file keeps the whole run for the next prune; a run the store holds as active is never deleted. A prune runs when the store opens and again once 50 run files more than the limit (or than the last prune left, when locked files stayed) are on disk, so a session does not list the folder on every write. The source of truth is local application data, not transient React state or demo seed records.

## Access boundary

File tools reject traversal and symlink escapes outside the selected project. Read-only mode disallows harness command execution and file writes. Workspace-write mode permits subprocesses with the current OS user's rights; `cwd` is not an OS sandbox. Native CLI providers apply their own documented access settings. The harness does not claim that it can sandbox arbitrary programs merely by validating command text.

Different chats may run concurrently in the same project, including write tasks. They share files: nothing isolates one chat from another. Prompts include other active tasks in overlapping folders and require preserving concurrent changes. The UI shows other active chats. A chat accepts only one active turn, including process cleanup. Cancelled/failed write processes still block new writes in overlapping folders until their operations settle. Inside one run, helpers share their parent's workspace by default and the model assigns them disjoint write responsibilities; a helper that edits files while others do is given its own git worktree copy of the workspace instead (*Isolated helpers*, below). `electron/worktree.mts` (the older write-lane helpers) remains an internal utility, not an execution path.

## Isolated helpers (git worktree copies)

```text
spawn_agent { isolation: 'worktree' }   snapshot of the parent's CURRENT state ──▶ git worktree <userData>/worktrees/<run>/<agent>
  helper edits its copy, in parallel with others                                   (node_modules linked, user's repo untouched)
  helper done ──▶ per-file 3-way merge into the target ──▶ merge report leads its result ──▶ parent's wait_agent returns
  run ends ──▶ unmerged changes → patch, links unlinked, worktree removed (a crash is swept at the next start)
```

**The argument.** `spawn_agent` takes `isolation`: `''` (default: the helper shares its parent's workspace), `'worktree'` (a git copy of the parent's workspace) or `'orbit'` (a git copy of Orbit's own repository, `restartHost.repoRoot`, to improve Orbit from any project's chat). It is refused with `isolation_unavailable` and an instruction (spawn without isolation and give disjoint files) when the run is read-only, the workspace is not inside a git work tree, or there is no Orbit repository; an unknown value is `invalid_isolation`. The copy is made last, after every other refusal (name reuse, limits, a pause that cut the caller's turn) and thrown away again if the registration that follows still fails.

**Making the copy** (`electron/agent-worktree.mts`, git through `electron/git.mts`). The source's current state is snapshotted without touching the user's index, HEAD, refs or files: a temporary index (`GIT_INDEX_FILE`; a copy of the real one, so unchanged files are not hashed again, else HEAD's tree), `add -A` (uncommitted and untracked-but-not-ignored files included), `write-tree`, `commit-tree` on top of HEAD with Orbit's identity from the environment (no git configuration is needed, signing is off). `git worktree add --detach` makes the copy under `<userData>/worktrees/<run>/<agent>` (a folder under the OS temp folder when the runtime has no data folder; never inside the source), with the user's hooks off, and the source's ignored `node_modules` (also the workspace's own) is linked into it: a junction on Windows, a directory symlink elsewhere. A `meta.json` per run folder lists the copies, the owning process and each copy's current base for the cleanup after a crash. Snapshots and merges into one folder are serialized, and so is git's worktree administration of one repository. A helper of an isolated helper shares its copy; one that is itself isolated is a worktree of the same repository made from the parent's copy (nested copies work down to `maxDepth`) and merges into the parent's copy.

**Where the helper works.** `AgentRecord.workspace` (absent: the run's) is what `util.agentWorkspace` returns: the provider's working folder, Orbit's file and command tools and the `workspace=` line of its prompt use it, and a note in the prompt says the workspace is an isolated copy that Orbit merges and that nothing may be committed, stashed or reset in it. The public agent field is `isolation { kind, path, base, target, merged?, conflicts? }`: `path` is the helper's workspace inside the copy, `target` the folder its changes merge into, `base` the snapshot it started from, `merged` the files merged so far and `conflicts` those that could not be. The project index never indexes a copy: an isolated helper's `index_search`/`index_outline` use the tree its files belong to (`util.logicalWorkspace`: the run's workspace, or Orbit's repository for an `'orbit'` copy). While the helper works its writes are not workspace changes, so they are neither file activity, nor change records, nor attributed command changes; they are recorded when they are merged (`reportMerge`: the helper's write in the FILE MAP, a change with the tool `merge` in the Changes tab, the router's notices), except for an `'orbit'` copy, whose files belong to another tree than the run's workspace.

**Merging back.** When an isolated helper completes (`completeAgent`, a follow-up's generation included, a budget or loop-guard handoff too) its changes are merged BEFORE it counts as done, so that the parent's `wait_agent`, `list_agents` and next turn see the result after the merge. What the helper changed against its base is read in the copy (`add -A` on the copy's own index, `diff --cached --raw -z --no-renames <base>`, limited to its workspace); each file is then merged into the target's working file, never through the target's index: the target's file is hashed as git would store it (so CRLF working files equal their LF blobs) and compared with the base and the helper's version. Unchanged in the target: the helper's file is copied (or deleted). Already equal: nothing. Changed on both sides: a three-way text merge with `git merge-file`, line endings normalised and restored (a CRLF file stays CRLF). A conflict (overlapping edits, a binary file, created on both sides with different content, deleted on one side and changed on the other, a link or submodule, a file too large to merge) leaves the target's file untouched and is recorded. Merged and already-equal paths move the copy's base up (a new commit on the old base through a temporary index), so that a later merge after a follow-up neither applies a change twice nor loses the target's own edits, and conflicting paths are tried again next time. The report (merged files; for each conflict where both versions are, and the `git -C <copy> diff <base> -- <file>` that shows what the helper changed) leads the helper's result, is traced and updates `isolation`; the parent applies the helper's change by hand or asks the helper with `followup_agent`. A merge that fails (the copy or the target is gone) says so in the same place and merges nothing.

**Taking the copies away.** When the run ends (finished, failed, stopped, restarted) the copies are removed in the background: first the provider processes of the run get up to 8 s to let go of their working folders (Windows locks them), then for each copy, newest first, the changes that never merged (conflicts, the work of a helper that failed or was stopped) are saved as a patch under `<worktrees>/patches/` (the newest 40 are kept; the patch and `git apply` are named in a `isolation` trace, added after the run's end), the links are unlinked (never followed: removing their target would delete the source's `node_modules`), `git worktree remove --force` runs with retries and a removal by hand as the last resort, and the worktree list is pruned. Nothing outside the worktrees folder is ever removed. At start the runtime host sweeps `<userData>/worktrees` the same way for runs that no longer exist (a crash, a restart that cut a cleanup short), leaving alone a folder whose owner process is alive (unless it is older than a week) or whose `meta.json` cannot be read.

**Limits.** A copy lives until its run ends, even after a clean merge (a follow-up goes on in it), and `git worktree list` in the repository shows the copies meanwhile. A helper the user stops is not merged: what it did stays in its copy and is saved as a patch when the run ends. `node_modules` is the original's: an install in the copy changes the original. Submodule contents are not in a copy, and links the helper makes are reported, not merged. Git hooks of the user's repository do not run for a copy. A very large untracked folder that the repository does not ignore is snapshotted and checked out like any other file. Orbit's own `read_file` cannot read a copy from the parent's workspace (it stays inside the workspace), so a conflict report names commands and paths instead.

Codex native multi-agent tools are disabled per process (`features.multi_agent=false`) in both exec and App Server transports. Orbit owns delegation, messages, cancellation and persistence. Orbit tool envelopes must be returned as the final provider response; commentary JSON is not executed. This avoids the invisible native-agent tree and ephemeral-thread collaboration failures. Readable reasoning summaries supplied by Codex are attributed to their Orbit agent; the UI does not fabricate unavailable reasoning. Inspector navigation stays outside the scrolling activity/correspondence pane.

## Runtime module map

`electron/runtime.mts` is the facade: it owns the state (runs, listeners, stores, the MCP server) and keeps the public surface (constructor options, methods, events); every method delegates to one function in `electron/runtime/` that receives the runtime instance first and calls the other modules only through those public methods, so no module reaches into another's state and no two modules require each other.

| Module | Concern |
|---|---|
| `util.mts` | shared helpers and constants (`bounded`, the single `clip`, `abortable`, agent views, `agentWorkspace` and `logicalWorkspace`: where an agent's files are, and which tree they belong to) and `diagnostics(runtime, run, where, error)`: an error the runtime deliberately survives leaves a trace of kind `diagnostic` instead of vanishing in an empty catch; it never throws and a finished run keeps none |
| `envelope.mts` | the JSON tool envelope: parsing a model response into content and tool calls (`parseResponse`) |
| `prompts.mts` | every text an agent is told (envelope tool guide, session system block, harness reminders) and the per-turn prompt assembly (`context`, `promptForTurn`, `resumePrompt`, team roster, FILE MAP) |
| `ledger.mts` | the transcript with tracked sizes and trimming, the work log (`describeCall`) and the collection of helper results |
| `store.mts` | snapshots, coalesced persistence, events to listeners, traces, agent updates, chat messages |
| `lifecycle.mts` | a run from start to end: payload validation and limits, the run record and root agent, earlier turns of the chat, finish, fail, stop, knowledge housekeeping |
| `agents.mts` | the agent tree: creation, scheduling, follow-ups, cancellation signals, model slots, the directory, completion (an isolated helper's changes are merged first) and the budget and loop-guard handoffs |
| `isolation.mts` | isolated helpers: the git worktree copy made for `spawn_agent {isolation}`, its merge into the target when the helper finishes, its removal when the run ends, the sweep of leftovers at start (the git and file work is `electron/agent-worktree.mts`) |
| `mailbox.mts` | team correspondence: send, read, wait, delivery marks, waking finished agents, `ask_team`, the prompt's mail block |
| `changes.mts` | file activity, change capture in the background, attributed commands, index readiness; what happens in an isolated copy is recorded when it is merged (`reportMerge`) |
| `turn.mts` | one provider turn (slot, budgets, timing record, cancellation) and its event stream (buffered traces, the root's streamed answer, native file events, the cut-off record) and the token counters (`recordUsage`: per agent and per run) |
| `handover.mts` | subscription failover as applied to an agent: preflight quota check, handover with its note, recovery after a refused or failed turn (the pure choice stays in `electron/failover.mts`) |
| `loops.mts` | `executeAgent`, the envelope loop (loop guard, poll budget, reminders) and the session loop (post-answer checks) |
| `session.mts` | transport choice, the in-process MCP server (its module imported on the first session) and its tokens, the `tools/list`, `approve` and `tools/call` (`dispatchMcp`) handlers with the per-call limit of a provider's MCP client, closing sessions |
| `tools.mts` | `executeTool`: the approval gate, shared notes, the improvement plan, workspace, index and team tools |
| `improvement.mts` | the endless improvement loop: the plan and handoff carried from the chat's previous run, `improvement_plan`, the progress block and the check of the root's answer |
| `knowledge.mts` | memory, skill and model-assessment tools and the memory usage marks |
| `restart.mts` | `restart_orbit` (where it is offered, its checks, the progress trace, the result or error), the `ORBIT_*` environment of the root agent's commands and CLIs, the restart note, the root of a continuation |

Outside the facade, `electron/agent-worktree.mts` holds the git and file work of isolated helpers (snapshots, worktree copies, merges, patches, the sweep) on top of `electron/git.mts`, and `electron/resume.mts` holds the runtime's side of restarts: the restart host that runs the self-upgrade script (with `inFlight()`, which `lifecycle.start` asks before it starts a run in another chat, and the cancel marker of a stop), reading and removing `pending-resume.json`, `markRestartingRuns` and `resumePending`. `electron/runtime-host.mts` builds the whole service (runtime, stores, quota monitor, restart host) and `electron/runtime-api.mts` implements its 26 call channels.
