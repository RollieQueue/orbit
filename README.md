# Orbit

Локальная оболочка для агента, который работает с вашими проектами через Codex CLI, Claude Code, Ollama или совместимый API. Проекты, разговоры, память и навыки принадлежат Orbit и сохраняются при смене модели. Агент сам выбирает действия, создаёт специалистов, получает их результаты и отвечает вам, а панель агентов показывает дерево делегирования, ход работы и результат каждого участника. Память трёх уровней — чат, проект и общая — и сохранённые навыки переживают перезапуск и доступны следующим задачам.

Установка CLI и вход в аккаунты не входят в Windows-пакет Orbit. Подробности подключения и ограничения транспорта: [docs/providers.md](docs/providers.md). Какую модель какой подписки звать под какую задачу — замер 16 моделей: [docs/MODEL-AUDIT.md](docs/MODEL-AUDIT.md).

История изменений по версиям: [docs/CHANGELOG.md](docs/CHANGELOG.md). Технический долг — что сделано и что осталось: [docs/TECH-DEBT.md](docs/TECH-DEBT.md).

## Как пользоваться

1. Выполните `npm install` и `npm run build`, затем запустите `Orbit.cmd` (или `npm start`) — Orbit стартует прямо из папки репозитория. Отдельная папка `Orbit-standalone-*` нужна только для распространения (`npm run package:win`).
2. Добавьте локальную папку или клонируйте Git-репозиторий. Обычные папки поддерживаются без `git init`.
3. В настройках выберите подключённого провайдера. Для Codex/Claude используется вход в их собственный CLI. Поле модели можно оставить пустым, чтобы использовать настройки CLI.
4. Создайте чат задачи и разговаривайте с агентом. Он сам выбирает действия, создаёт специалистов, получает их результаты и отвечает вам.
5. Откройте панель агентов, чтобы увидеть дерево делегирования, ход работы и результат каждого участника. Переключение чата или проекта не прерывает задачу.

Браузерный `npm run dev` без Electron показывает интерфейс; запуск агентов и доступ к файлам требуют desktop-приложения.

Выбор модели, уровня мышления и доступа находится рядом с полем сообщения. Ask показывает запросы разрешения; Full access запускает задачу без подтверждений. Доступ наследуется всеми подагентами. Уровень мышления доступен для Codex и совместимого API.

### Какую модель получает помощник

Создавая помощника, агент может назвать тип поручения: код, ревью, поиск (найти и прочитать код, мелкая правка, прогон проверок) или текст для пользователя. Тогда модель выбирает Orbit по таблице `electron/model-routing.json`, составленной по [замеру моделей](docs/MODEL-AUDIT.md). Например, ревью сначала достаётся GPT-6 Astra (Codex), затем Opus 5.5 и Gemini 3.1 Pro. Orbit пропускает подписки, которые не подключены, не входят в пул провайдеров, недавно не ответили или почти исчерпали квоту для этой модели. Порог тот же, что у автозамены подписки в разделе «Квоты». Агент видит, какую модель получил помощник, какие пропущены и почему; это же записывается в ход работы. Если агент сам назвал модель, Orbit её не меняет. Claude Fable 5.1 в таблицу не входит.

### Пауза и остановка агентов

- **Пауза.** Кнопка паузы в чате (рядом со «Стоп») останавливает основного агента вместе со всеми помощниками. В инспекторе панели агентов («Пауза» под вкладками) так же останавливается любой агент со своими подагентами. Текущий ход прерывается сразу, новых ходов и вызовов инструментов нет. Задача, сессия, переписка и файлы сохраняются.
- **Продолжить.** Агент продолжает ту же сессию и узнаёт, что его ход был прерван и что он успел сделать. Прерванный ход не засчитывается в лимит ходов. Если сессию после прерывания возобновить нельзя, агент один раз начинает новую с той же записью. Помощник, которого вы поставили на паузу отдельно, ждёт своей кнопки «Продолжить».
- **Остановить.** Есть только у помощников. Помощник и его подагенты завершаются. Руководитель сразу узнаёт об этом, даже если ждёт сообщения, получает, что помощник успел сделать, и продолжает без него. Весь запуск останавливает «Стоп» в чате.
- Сообщение агенту на паузе ставится в очередь, и агент прочитает его после «Продолжить» как ваше указание, даже если пауза застала его в ожидании сообщения или помощников.

Счётчик под «Агент работает» и в инспекторе показывает действия агента: команды, правки и вызовы инструментов Orbit. Ход — один запуск модели: Claude и Codex в режиме сессии выполняют за один ход всю задачу, поэтому число ходов почти не растёт. Пока модель Claude размышляет (текста её размышлений поток не показывает, и на большом уровне рассуждений это длится минутами), строка продолжается словами «думает · ~N тыс. токенов»: это примерная оценка Claude CLI для текущего размышления. Когда модель начинает писать или вызывает инструмент, надпись исчезает.

### Сообщения работающему агенту

Пока агент работает, поле сообщения в чате пишет основному агенту, а поле в инспекторе панели агентов — выбранному агенту. Сообщение доходит сразу, а не в конце хода. Если агент вызывает инструмент Orbit, сообщение приходит вместе с результатом. Если такого вызова нет, Orbit через 2 секунды прерывает ход между шагами, и агент продолжает ту же сессию уже с вашим сообщением; прерванный ход не засчитывается в лимит. Ход не прерывается посреди команды и посреди обдумывания: если модель уже думает или пишет, она сначала заканчивает шаг, и сообщение приходит сразу после её следующего инструмента или, если шаг кончился ответом, следующим ходом. Иначе обдуманное терялось бы, и модель думала бы заново. Так же сразу доходит до помощника сообщение его руководителя, то есть любого агента выше в команде. Сообщения помощников друг другу ход не прерывают.

Если сообщение пришло, когда ответ уже был готов, агент получает ещё один ход, чтобы его обработать. Если этот ход не удался (например, упал провайдер), вы получаете готовый ответ, а под ним — пометку Orbit о том, что сообщение осталось без ответа, с началом его текста. Если сообщение ещё нужно, отправьте его снова.

### Файлы и изображения в чате

Кнопка со скрепкой у поля сообщения прикрепляет документы и изображения. Файлы можно также перетащить на поле или вставить из буфера обмена (Ctrl+V). За одно сообщение — до 10 файлов, каждый до 20 МБ, всего до 50 МБ. Orbit сохраняет их в папке `attachments/` своих данных. Агент получает пути к файлам и читает их своими инструментами; Claude видит изображение, когда читает файл, в любом режиме доступа. Файлы можно прикрепить и к первому сообщению задачи, и к сообщению работающему агенту. Сообщение может состоять из одних файлов. В чате они показаны под сообщением: изображения до 2 МБ миниатюрами, по щелчку файл открывается. Пока файлы сохраняются, под сообщением видны их названия. Если Orbit отклонил отправку, сохранённые копии удаляются, а файлы возвращаются в поле сообщения. Удалённый чат забирает с собой свою папку вложений. Файл, открытый в этот момент в другой программе (например, PDF в просмотрщике), Windows удалить не даёт: Orbit удалит его позже, при следующем удалении чата или при запуске. Когда агент перезапускает Orbit, чтобы применить свои изменения, продолжение задачи снова получает пути её файлов.

## Бесконечное улучшение

Переключатель «Бесконечное улучшение» над полем сообщения (он же есть в настройках) включает цикл. Ваше сообщение становится целью цикла, и за один запуск агент делает пачку задач плана (до четырёх независимых; каждую параллельно выполняет помощник в своей изолированной копии):
1. реализует и проверяет их;
2. закрывает каждую в плане (`improvement_plan`);
3. применяет один раз на всю пачку. Если менялся код самого Orbit, это делает `restart_orbit`: проверки, сборка и перезапуск нужной части. Он доступен в чате любого проекта, не только репозитория Orbit; в чате другого проекта он нужен, только когда изменился код Orbit (изменения самого проекта перезапуска не требуют). Нужен ли он, Orbit решает, сравнивая код на диске с кодом, который сейчас работает: изменение, сделанное любым способом (хоть командой оболочки), надо применить, а отменённая правка перезапуска не требует.

Когда запуск завершился, Orbit сам начинает следующую задачу новым запуском в том же чате. История чата в запрос не попадает: модель получает цель, план (открытые задачи и последние сделанные) и короткую передачу от предыдущей задачи, поэтому контекст не копится. Над чатом видна полоса «∞ Бесконечное улучшение · задача N» с состоянием и кнопками «Остановить цикл» и «Запустить сейчас».

- **Остановка.** Цикл идёт, пока переключатель включён. Его останавливают выключение переключателя, «Стоп» (прерывает текущую задачу) и «Остановить цикл» (текущая задача доработает). Закрытие Orbit и перезапуск runtime цикл не останавливают: прерванная задача повторится. Новое сообщение с включённым переключателем запускает цикл снова. Во всём Orbit активен один цикл: сообщение с включённым переключателем в другом чате переносит цикл туда. Второй цикл держал бы чат постоянно занятым, а `restart_orbit` не перезапускает Orbit, пока работают другие чаты.
- **Повторы.** Ошибка, обрыв или задача, которая ничего не закрыла, повторяются через 1, 3 и 10 минут, дальше каждые 30 минут. Если Orbit ещё занят (завершаются процессы прошлой задачи или другой чат применяет `restart_orbit`), старт повторяется через 5–30 секунд и неудачей не считается; полоса пишет «ждёт, пока Orbit освободится…». Ваши сообщения в этом чате во время цикла попадают в запрос следующих задач.
- **Пауза.** Цикл встаёт на паузу до вашего сообщения, если выполнена цель с числом («сделай 5 улучшений») или без вас дальше нельзя. Паузу ставит только причина, найденная в текущей задаче, а не старая блокировка; пауза, поставленная перед `restart_orbit`, сохраняется после перезапуска.
- **Предел перезапусков.** Orbit перезапускается не больше трёх раз за 30 минут (`ORBIT_UPGRADE_MAX_CYCLES`). Если задачи идут чаще, изменение задачи остаётся проверенным и устанавливается при перезапуске следующей задачи.

## Подключение провайдеров

**Codex / Claude Code:** установите CLI и выполните вход в нём. Orbit проверяет доступность CLI и авторизацию, но не копирует учётные данные. Для нестандартного пути задайте `ORBIT_CODEX_COMMAND` или `ORBIT_CLAUDE_COMMAND`.

**Ollama:** запустите локальный сервер с уже установленной моделью. Выберите модель в Orbit или задайте `ORBIT_OLLAMA_MODEL`. Orbit самостоятельно не скачивает модели. Адрес сервера меняется через `ORBIT_OLLAMA_URL`.

**Совместимый API:** перед запуском Orbit задайте переменные среды, например в PowerShell:

```powershell
$env:ORBIT_OPENAI_BASE_URL = 'http://127.0.0.1:1234/v1'
$env:ORBIT_OPENAI_MODEL = 'your-model-id'
# ORBIT_OPENAI_API_KEY — только если сервер требует ключ.
npm start
```

Адрес Ollama или совместимого API на другом компьютере указывается с `https://`. По `http://` запросы агентов (а у совместимого API ещё и ключ) идут по сети незашифрованными, поэтому такой адрес Orbit принимает только для этого компьютера (`localhost`, `127.x.x.x`, `[::1]`). Если сеть доверенная (например, Ollama стоит на другом компьютере дома), задайте `ORBIT_ALLOW_INSECURE_HTTP=1`.

Подробности транспорта, ограничений доступа и официальные источники: [docs/providers.md](docs/providers.md).

## Память и развитие

Память содержит факты, предпочтения и решения и делится на три уровня.

| Уровень | Что хранит | Как уходит |
|---|---|---|
| Чат | рабочие заметки одной задачи: ограничения, принятые решения, что осталось сделать | не используется 30 дней; чат удалён; или поднимается в проект, если чат к записи возвращался |
| Проект | проверенные знания об одной кодовой базе, общие для всех её чатов | вытесняется по ценности при заполнении (250 записей) |
| Общая | то, что верно во всех проектах: предпочтения, общие приёмы, оценки моделей | вытесняется по ценности при заполнении (200 записей) |

Память не разрастается. У каждого уровня есть лимит; ценность записи складывается из уверенности, свежести и числа использований, поэтому невостребованное вытесняется первым. Закреплённые и написанные вами записи не вытесняются и не перезаписываются агентами. Агент, повторно записавший то же самое, обновляет существующую запись, а не создаёт копию; после каждого завершённого запуска дубликаты объединяются, устаревшее удаляется. Оценки моделей ограничены 60 записями. Заметка, слово в слово совпавшая в двух и более проектах и не называющая ни один из них, переезжает в общую память; похожая, но отличающаяся, например, числом или названием инструмента, не переезжает.

В промпт попадает не вся память, а подборка: закреплённое, затем найденное по задаче (индекс BM25 с учётом словоформ русского и английского), затем самое ценное; остальное перечислено заголовками, полное содержимое агент получает через `memory_search`. Общая память отключается для проекта переключателем, и тогда проект не читает и не пишет ни общие заметки, ни общие навыки и не участвует в их пополнении.

Навык содержит название, назначение, условия применения и инструкции, которые агент загружает по необходимости. Агент находит подходящий навык по задаче, применяет его и сообщает результат (`worked`, `partial`, `failed`); замечание к неудаче сохраняется как «подводный камень» для следующего агента. После содержательного запуска (10 и более ходов) или запуска, где применялся навык, оркестратор один раз получает напоминание оценить применённые навыки и сохранить новый, если в работе появилась повторяемая процедура: например, поднять изолированную копию окружения в Linux. Навык, привязанный к проекту, остаётся в нём; независимый от проекта агент сохраняет как общий.

Например: «После исправления запомни, как здесь запускать проверки» или «Создай вспомогательный скрипт для этой проверки, проверь его и сохрани навык для следующих задач». Решение о сохранении принимает модель через инструменты, а записи можно просмотреть, закрепить, выключить и удалить в интерфейсе. Выключенный навык остаётся в панели, но агенты его не видят.

### Навыки — любые дополнения, которые Orbit делает для себя

Навык — не только текст процедуры. Это любое дополнение за рамками встроенных возможностей Orbit: полезная инструкция с командами, анимация празднования, скрипты, которые, например, поднимают Linux. Код самого Orbit агент улучшает отдельно (`restart_orbit`), а навык живёт рядом и включается или выключается одним переключателем.

У навыка всегда есть название, описание и инструкции для агентов. Кроме того, навык может нести пакет файлов (страницы, скрипты, картинки) и три механизма, которые понимает Orbit:
- **параметры** — значения, которые вы меняете в карточке навыка (ссылка, отрезок, надпись, флажок). Агент видит их текущие значения, и его правка навыка ваши значения не сбрасывает;
- **триггер** — событие, на которое Orbit сам запускает навык. Пока одно: задача выполнена. Тогда Orbit показывает страницу из пакета во весь экран, в изолированном фрейме без доступа к Orbit. Если задача применяла изменения через `restart_orbit`, страница откроется после перезагрузки, когда завершится продолжение задачи;
- **команды** — именованные команды, которые агент запускает в папке пакета.

Агент создаёт навык инструментом `capability_install`: передаёт файлы прямо в вызове или собирает и проверяет пакет в папке, а потом ставит его через `fromDir`. Манифест `skill.json` в папке задаёт название, описание, параметры, триггер и команды. `capability_read` отдаёт инструкции, папку пакета, файлы, параметры, триггеры и команды. В панели «Навыки» на карточке видно, что есть в навыке (инструкция, страница по событию, команды, файлы). Там же переключатель, форма параметров и кнопки «Показать» (открыть страницу сейчас) и «Открыть папку». Навык с файлами, триггером или командами не вытесняется и не сливается с похожими, а агент меняет его только по id. Выключенный навык агенты не видят, и его триггер не срабатывает.

Пример — празднование выполненной задачи, пакет `skills/task-completed-celebration/`. Во весь экран играет отрезок видео YouTube со звуком (по умолчанию https://www.youtube.com/watch?v=6-8E4Nirh9s, с 42-й по 73-ю секунду) и сыплется конфетти. Надпись TASK COMPLETED в стиле WordArt из PowerPoint крутится вокруг своей оси и летает по экрану, как логотип DVD. Ссылка, отрезок, надпись и конфетти — параметры навыка. Празднование закрывается кликом, Esc, кнопкой × или само по окончании отрезка. Без сети остаются конфетти и надпись. Если системный прокси Windows выключен, окно Orbit ходит в YouTube через прокси из `HTTPS_PROXY` и `HTTP_PROXY`, как агенты, поэтому видео играет и там, где YouTube доступен только через такой прокси. Если в Windows выключена анимация, движется только видео: надпись стоит посередине, конфетти лежит по краям экрана. Агент ставит пакет командой `capability_install` с `fromDir`, указывающим на эту папку.

Это развитие через проверенные процедуры, скрипты и память. Код самого Orbit можно подключить как обычный проект и изменять тем же агентом: когда Orbit запущен из своего репозитория, агент применяет изменения инструментом `restart_orbit` и продолжает задачу после перезапуска (см. «Самообновление»). Улучшать себя агент может и из чата любого другого проекта: в запросе он получает блок `YOUR OWN CODE` с путём к репозиторию Orbit, правки делает помощник в изолированной копии репозитория (при полном доступе агент может править репозиторий и сам), `restart_orbit` применяет их, а чат продолжается в своём проекте. Собранный дистрибутив `Orbit-standalone-*` сам себя не обновляет.

## Хранение и ограничения

Данные сохраняются в Electron `userData` (обычно `%APPDATA%/orbit-ide`):

- `workspace-state.json` — проекты, чаты и настройки;
- `memory.json` — память всех трёх уровней (чат, проект, общая);
- `capabilities.json` — навыки, их предыдущие версии и статистика применения;
- `skills/` — файлы навыков-пакетов (страницы, скрипты), по папке на навык;
- `attachments/` — файлы, прикреплённые к сообщениям чата, по папке на чат (удаляется вместе с чатом);
- `run-history/` — агенты, действия, результаты запусков и файлы, которые каждый агент читал или менял; хранятся 500 последних запусков, более старые удаляются вместе с резервными копиями и картинками;
- `project-index/` — индекс проектов (пересобирается при повреждении);
- `pending-resume.json` — намерение продолжить запуск после перезапуска по запросу агента (пишет скрипт самообновления, runtime читает и удаляет).

Сохраняются резервные копии JSON. Работавшие в момент аварийного завершения задачи при следующем запуске помечаются прерванными. Закрытие приложения останавливает процессы; после запуска продолжите задачу сообщением в сохранённом чате. Исключение — запуск, который агент завершил перезапуском Orbit (`restart_orbit`): он получает статус «Перезапуск Orbit» и продолжается сам. Отдельного постоянно работающего фонового сервиса пока нет.

В режиме чтения файловые изменения и команды оболочки через инструменты Orbit запрещены. В режиме работы с проектом файловые инструменты ограничены его папкой и проверяют символические ссылки. Команды процессов имеют права пользователя ОС; рабочая папка сама по себе не является системной песочницей. Дополнительные ограничения Codex/Claude описаны в документации адаптеров. Разные чаты могут работать параллельно в одной папке, включая запись. Файлы общие: поручайте изменения разных участков. В одном чате одновременно выполняется один запуск; после остановки нужно дождаться завершения его процессов. Внутри одного роя агент должен разделять файлы между специалистами.

Поддерживаются шесть адаптеров: Codex, Claude Code, Antigravity, Cursor, Ollama и совместимый API. OpenCode не подключён. Качество планирования и делегирования зависит от выбранной модели. Финальный ответ модели не подменяет результат тестов: фактические команды и ошибки видны в журнале агента.

## Сборка и обновления

Отдельная сборка для работы не нужна. Главный процесс и runtime (`electron/`) Node выполняет прямо из исходников, а `npm run build` за доли секунды собирает только интерфейс окна в `dist/`. Поэтому:

- первый запуск: `npm install`, `npm run build`, затем `Orbit.cmd` или `npm start`;
- после правки runtime (всё в `electron/`, кроме файлов оболочки — `SHELL_FILES` в `electron/fingerprint.cjs`): `Orbit.cmd --restart-runtime` или «Настройки» → «Перезапустить runtime» — новый процесс runtime за доли секунды, окно остаётся открытым;
- после правки файлов оболочки (`main.cjs`, `preload.cjs`, `ipc-*.cjs`, `runtime-client.cjs`, `fingerprint.cjs`, `git.mts`, `runtime-protocol.mts`, `package.json`): `Orbit.cmd --relaunch` — перезапуск работающего экземпляра целиком за 1–2 с;
- после правки `src/`: `npm run build` и `Orbit.cmd --reload-renderer` (перезагружается только окно), либо работайте через `npm run dev`, где интерфейс обновляется без перезапуска;
- цикл, который делают агенты сами: `npm run self-upgrade` или инструмент `restart_orbit` (проверки → сборка интерфейса, если он менялся → перезапуск нужного уровня → файл здоровья → откат при неудаче);
- `npm run package:win` нужен только для дистрибутива в отдельной папке `Orbit-standalone-*`; для обновлений он не используется, а накопившиеся папки показывает и удаляет `npm run clean:bundles`.

## Разработка и проверки

```powershell
npm install
npm run build          # tsc --noEmit + vite build → dist/ + запись сборки dist/orbit-build.json
npm start              # Orbit из репозитория (то же, что Orbit.cmd)
npm run dev            # Vite с HMR + Electron (ORBIT_DEV=1)
npm test
npm run smoke
npm run smoke:desktop
npm run verify
npm run self-upgrade
npm run clean:bundles
npm run package:win    # отдельный дистрибутив Orbit-standalone-*; цикл обновления его не вызывает
```

Приложение запускается прямо из папки репозитория: `Orbit.cmd` (и `npm start`) выполняет `node_modules\electron\dist\electron.exe <репозиторий>`, главный процесс берётся из `electron/main.cjs`, runtime работает в отдельном процессе (`electron/runtime-child.cjs`), интерфейс — из `dist/`, данные — из `%APPDATA%/orbit-ide`, как и раньше. Если нет `dist/index.html` или `node_modules/electron`, `Orbit.cmd` завершается с понятным сообщением. Аргументы передаются дальше; если Orbit уже работает, второй экземпляр только передаёт ему сигнал и завершается (обработчик `second-instance` в `electron/main.cjs`): `--relaunch` — перезапуск целиком (runtime сохраняет состояние и останавливает запуски, затем `app.relaunch`), `--restart-runtime` — только процесс runtime, `--reload-renderer` — только окно. Если Orbit не запущен, он просто запускается. Через `npm start` флаги передаются после `--`: `npm start -- --restart-runtime`. Окно может само вызвать перезапуск целиком (`window.orbit.relaunch()`) и перезапуск runtime (`window.orbit.restartRuntime()`).

Тесты используют управляемые провайдеры и локальный HTTP-сервер; они не тратят квоту модели. Desktop-проверка запускает настоящий Electron, preload, IPC и runtime в отдельном процессе во временном профиле и перезапускает runtime через «Настройки»; провайдеры и квоты ей подменяет `scripts/smoke-fixtures.cjs` (переменная `ORBIT_RUNTIME_FIXTURES`), а с `ORBIT_SMOKE=1` runtime без этих подмен не стартует. `npm run package:win` по-прежнему собирает отдельную папку `Orbit-standalone-*` для распространения (внутри неё `Orbit.cmd` запускает `Orbit.exe`). `npm run clean:bundles` показывает накопившиеся `Orbit-standalone-*`, `release*` и `.orbit-partial-*` с размерами и ничего не удаляет; `npm run clean:bundles -- --yes` удаляет их, оставляя новейшую сборку (`--all` — и её).

IPC между окном и главным процессом описан одной таблицей в `electron/ipc-contract.cjs` (метод → канал → аргументы → тип результата, плюс push-события `runtime:event`, `quota:update`, `restart:notice` и `runtime:status-changed`). Из неё генерируются `electron/preload.cjs` целиком и блок `OrbitBridge` в `src/vite-env.d.ts` (между маркерами `BEGIN/END generated`): после правки таблицы выполните `node scripts/gen-ipc-types.cjs` (`--check` только сообщает о расхождении); `tests/ipc-contract.test.cjs` падает, если сгенерированные файлы устарели. На восемь каналов главный процесс отвечает сам (`electron/ipc-handlers.cjs`: выбор, осмотр и клонирование папки проекта, внешние ссылки, `app:ping`, `app:relaunch`, `runtime:restart`, `runtime:status`), остальные 26 передаёт процессу runtime, где их обрабатывает `electron/runtime-api.mts`; при старте проверяется, что у каждого канала таблицы есть обработчик и наоборот.

Инструмент агентов `run_command` по умолчанию ждёт 600 с (`timeout_ms` от 20 мс до 3 600 с), поэтому цикл обновления или длинный прогон тестов, запущенный из чата, не обрывается.

## Самообновление

`npm run self-upgrade` — живой цикл: блокировка → typecheck (оба tsconfig) → `node --experimental-strip-types --test tests/*.test.cjs` → runtime smoke → `tests/main-load.test.cjs` (проверки пропускаются с `--no-verify`, а также если `dist/orbit-build.json` записал, что ровно эти исходники их уже прошли) → проверенные `electron/` и `src/` снимаются в `refs/orbit/self-upgrade/candidate` (новые файлы тоже; индекс git не трогается) → `vite build`, только если входы интерфейса (`src/`, `index.html`, `vite.config.ts`, `tsconfig.json`, `package.json`) не те, из которых собрана `dist/` (перед сборкой `dist/` сохраняется в `dist-prev/`), так что правка одного runtime сборки не требует → работающему Orbit посылается сигнал выбранного уровня (`electron.exe <репозиторий> <флаг>`, то же, что `Orbit.cmd <флаг>`, с профилем работающего экземпляра в `ORBIT_USER_DATA`; без работающего экземпляра Orbit просто запускается) → ожидание до 15 с свежего `artifacts/self-upgrade-health.json` (или файла из `ORBIT_HEALTH_FILE`, куда его тогда пишет главный процесс; при `ORBIT_HEALTH_FILE=0` отчёта нет, и скрипт ничего не перезапускает: статус `no-health-report`). Запись сборки `dist/orbit-build.json` (из каких входов собрана `dist/`) делает и обычный `npm run build`: он вызывает `node scripts/self-upgrade.cjs --mark-build`, и такая запись не утверждает, что проверки пройдены. Отчёт здоровья главный процесс пишет отдельно для запуска (окно ответило через preload и показало интерфейс, runtime готов), для каждого перезапуска runtime (новый runtime готов и всё ещё готов после того, как окно снова прошло ту же проверку, при необходимости после одной перезагрузки) и для каждой перезагрузки окна: `{ ok, pid, startedAt, level, generation, restartedAt, commit, distMtime, shellHash, runtimeHash, rendererHash, rendererSource, runtime: { mode, ready, pid, ms } }`, где `shellHash` и `runtimeHash` — отпечатки загруженного кода, а `rendererHash` — входов интерфейса, который показывает окно (из записи загруженной сборки, `rendererSource: 'build'`, иначе с диска, `'files'`); при `did-fail-load`, аварии рендерера или исключении до готовности — `{ ok: false, error }`. Старт или перезапуск runtime, прерванный закрытием или перезапуском Orbit, отчёта не получает. Сборок `Orbit-standalone-*` и electron-builder в цикле нет.

**Уровень перезапуска.** Скрипт сравнивает отпечатки файлов на диске (`electron/fingerprint.cjs`: sha1 файлов оболочки — `SHELL_FILES`, отдельно всех остальных файлов `electron/` и отдельно входов интерфейса, CRLF считается как LF) с последним отчётом работающего экземпляра — до проверок и ещё раз после них — и выбирает самый дешёвый перезапуск:

- `full` (`--relaunch`): изменились файлы оболочки (главный процесс, preload, IPC, клиент runtime, `package.json`); изменились и runtime, и интерфейс (перезапуск runtime оставил бы в окне старую сборку); Orbit не запущен, его отчёта нет, он неудачен, без отпечатков или принадлежит другому экземпляру этого репозитория (другой профиль, не тот, что в `ORBIT_USER_DATA`); runtime работает внутри главного процесса (`ORBIT_RUNTIME_MODE=inprocess`);
- `runtime` (`--restart-runtime`): изменились только остальные файлы `electron/` — новый процесс runtime, окно остаётся открытым, идущие запуски прерываются;
- `renderer` (`--reload-renderer`): изменились только входы интерфейса — их отпечаток не тот `rendererHash`, что у окна (для старого отчёта без него: новая сборка или `dist/` новее той, что показывает окно), — окно перезагружает новую сборку, runtime и его запуски продолжают работать;
- применять нечего: `status: up-to-date`, код выхода 0.

`--level full|runtime|renderer` задаёт уровень вручную (`runtime` при `inprocess` становится `full`), `--force` проверяет и пересобирает заново, то есть как минимум перезагружает окно.

Удачный перезапуск делает снимок `refs/orbit/self-upgrade/last-good`. Неудача (нет свежего отчёта за 15 с или `ok: false`): неудачные исходники сохраняются в `refs/orbit/self-upgrade/failed` и `artifacts/self-upgrade-failed.patch`, дальше откат по уровню. `full`: процессы Orbit этого репозитория останавливаются, возвращаются `electron/` + `src/` и `dist-prev/` (если этот прогон собирал интерфейс), Orbit запускается снова. `runtime`: возвращаются файлы runtime в `electron/` (файлы оболочки работающего главного процесса остаются), runtime перезапускается ещё раз. `renderer`: возвращаются `dist-prev/` и `src/` (если этот прогон собирал интерфейс), окно перезагружается. Если повтор уровня `runtime` или `renderer` тоже не удался, Orbit останавливается и запускается заново. Отчёт получает `status: rolled-back`. Исходники возвращаются через временный индекс git (настоящий индекс и его блокировка не участвуют; до трёх попыток с паузой 0,5 с) поверх рабочей копии: из файлов, которых нет в базе отката, удаляются только те, что добавила неудачная правка (отчёт перечисляет их в `rollback.deleted`), а файлы, созданные позже, — неотслеживаемые, добавленные в индекс или закоммиченные — остаются. Неудавшийся возврат называется в отчёте и в ошибке намерения. Вернуть неудачную правку: `git restore --source=refs/orbit/self-upgrade/failed --worktree -- electron src`.

**База отката.** Исходники возвращаются только к коду, который работал до перезапуска, и отдельно по частям: `electron/` — к снимку с теми отпечатками оболочки и runtime, что в отчёте работавшего экземпляра, `src/` — к снимку с его `rendererHash` (то, что показывало окно). После каждого здорового отчёта — запуска, перезапуска runtime и перезагрузки окна — главный процесс в фоне выполняет `node scripts/self-upgrade.cjs --record-running --pid … --started-at … --shell-hash … --runtime-hash … --renderer-hash …` (только при запуске из репозитория): снимок `electron/` + `src/` через временный индекс git (настоящий индекс и `git stash` не используются) становится `refs/orbit/self-upgrade/running`, запись — `artifacts/self-upgrade-running.json` (версия 2); если файлы на диске уже не тот код, который загрузил экземпляр, ничего не записывается, а если `src/` на диске не то, что показывает окно, запись получает `rendererHash: null`. Кандидаты — эта запись (если её pid и время старта совпадают с экземпляром, работавшим до перезапуска) и `last-good` (по отпечаткам в сообщении снимка); берётся тот, что подходит большему числу частей (при равенстве — запись). Часть, для которой подходящего снимка нет, не трогается, и отчёт с ошибкой намерения это называют (например, «src/ left as it is (no trustworthy rollback base)»); прежняя `dist/` возвращается и тогда, если этот прогон её пересобрал. `npm run self-upgrade:check` (`--dry-run`) показывает план, выбранный уровень и `rollbackBase`.

Фаза перезапуска выполняется отдельным процессом-наблюдателем, отвязанным от дерева процессов вызывающей команды: когда обновление запускает агент внутри Orbit, перезапуск runtime или всего приложения останавливает его команды, а проверка здоровья и откат должны это пережить. Отчёт с временем каждого шага: `artifacts/self-upgrade-last.json` (в том числе `status`, `level`, `levelReason`, `intentFile`, `intentWritten`, а после упавшей проверки — `failures`: упавшие тесты и ошибки TypeScript с сообщением и местом; их же список печатается последним в выводе, который получает агент); весь вывод проверок и сборки последнего запуска: `artifacts/self-upgrade-checks.log`; журнал наблюдателя: `artifacts/self-upgrade-watch.log`. Флаги: `--dry-run` (план, уровень, база отката и проверка инструментов: tsc, vite, `electron.exe`, git), `--no-relaunch` (проверить и собрать, не перезапускать), `--verify-only`, `--no-verify` (без typecheck, тестов, smoke и main-load; сборка, перезапуск, проверка здоровья и откат остаются), `--desktop` (добавить `smoke:desktop`), `--force`, `--level auto|full|runtime|renderer`, `--reason <текст>` и `--continue-with <текст>` (причина перезапуска и что делать после него — для намерения продолжить), `--intent-file <путь>` (куда писать намерение; по умолчанию `ORBIT_RESUME_FILE`), `--record-running`, `--mark-build` (записать `dist/orbit-build.json` для только что собранной `dist/`, без отметки о проверках; его вызывает `npm run build`). Правка исходников во время проверок отменяет перезапуск (`dist/` возвращается из `dist-prev/`). Одновременно работает один цикл: блокировку `artifacts/self-upgrade.lock` (`{ pid, nonce, role, startedAt }`) держатель обновляет каждые 10 с, она считается брошенной через 60 с без обновления или когда её процесс завершился, а наблюдатель принимает её от основного процесса по `nonce`. Не больше `ORBIT_UPGRADE_MAX_CYCLES` (3) перезапусков уровня `runtime` или `full` за `ORBIT_UPGRADE_CYCLE_WINDOW_MIN` (30) минут, перезагрузки окна не считаются; таймаут здоровья — `ORBIT_UPGRADE_HEALTH_TIMEOUT_MS`. Под `npm run dev` (`ORBIT_DEV=1`) скрипт ничего не перезапускает (`status: dev-mode`: перезапуск остановил бы сервер Vite), а `--dry-run`, `--no-relaunch` и `--verify-only` работают. Коды выхода: 0 — применено или нечего применять, 1 — ошибка (аргументы, инструменты, проверки, сборка, откат), 2 — предел циклов, блокировка, `dev-mode`, отмена или наблюдатель не отчитался вовремя. Старые сборки код не удаляет — только `npm run clean:bundles -- --yes` по запросу.

**Перезапуск по запросу агента.** Корневой агент применяет изменения в коде самого Orbit инструментом `restart_orbit { reason, continueWith, verify = true }`. Инструмент предлагается (в описании инструментов и в списке MCP) и принимается только у корневого агента запуска с доступом на запись, в чате любого проекта (рабочая папка не важна: скрипт самообновления всегда работает в репозитории, из которого запущен Orbit, а продолжение задачи стартует в том же чате и в той же папке; корню запуска в другом проекте запрос дополнительно сообщает, где лежит код Orbit), при запуске Orbit из репозитория (есть `scripts/self-upgrade.cjs` и `.git`) и не под `npm run dev` (`ORBIT_DEV=1`: перезапуск остановил бы сервер Vite); в Ask он сначала спрашивает разрешение. Пока работают запуски других чатов, он отказывает и перечисляет их (агенту предлагается подождать через `wait_message` и повторить) и проверяет это ещё раз после ответа на запрос разрешения; помощники своего запуска не мешают. Пока работает скрипт, новые запуски в других чатах отклоняются: «Orbit сейчас применяет изменения своего кода и перезапустится; отправьте сообщение после перезапуска.» Runtime выполняет `node scripts/self-upgrade.cjs [--no-verify] --reason … --continue-with …`, вывод скрипта агент видит одной обновляемой трассой. Неудачная проверка, предел циклов или блокировка возвращают агенту ошибку со статусом, кодом выхода и последними 80 строками вывода; ничего не перезапускается, агент исправляет код и вызывает снова. Ошибка отката называет базу отката, `artifacts/self-upgrade-failed.patch` и `refs/orbit/self-upgrade/failed` и просит сначала вернуть правку (`git restore --source=refs/orbit/self-upgrade/failed --worktree -- …`), а потом чинить. Если применять нечего, инструмент так и отвечает. Уровень `renderer`: окно перезагружается, запуск продолжается. Уровни `runtime` и `full`: перед сигналом скрипт пишет `<userData>/pending-resume.json`; runtime, останавливаясь, завершает запуск статусом `restarting` («Перезапуск Orbit») и записывает на нём идентификатор этого намерения, а вызов `restart_orbit` сразу заканчивается. Новый runtime после здорового старта ждёт подтверждения наблюдателя (`verdict: 'relaunched'`, до 30 с), удаляет намерение (не вышло — переименовывает в `pending-resume.json.consumed`; не вышло и это — продолжения нет) и сам начинает в том же чате новый запуск с теми же настройками: сообщение — `continueWith` и абзац «Orbit перезапущен с новым кодом (коммит … + незакоммиченные изменения, снимок …, уровень …, причина: …); предыдущий запуск … завершён перезапуском…». Корневой агент продолжения получает заметку о прерванном запуске (журнал действий, файлы, помощники, оборванный ход, требование сверить реальное состояние перед повтором записи или команды) и, если остался на том же провайдере в сессионном режиме, продолжает прежнюю сессию провайдера (у Claude — и когда `restart_orbit` был вызван в первом ходе). В чате появляется заметка («Orbit перезапущен по запросу агента, задача продолжена» и др.), в панели агентов — ссылки «Продолжение запуска …» и «Продолжен в …»; пока продолжение не началось (не дольше 2 минут), чат занят: отправить сообщение или удалить чат нельзя, подсказка — «Orbit перезапускается, задача продолжится автоматически». Продолжение не запускается, если перезапуск откатился (в чат пишутся ошибка и путь к `artifacts/self-upgrade-failed.patch`), наблюдатель сам завершился с ошибкой (`verdict: 'failed'`), намерению больше 30 минут (без подтверждения наблюдателя — больше 10), перезапусков подряд вместе с этим набирается `ORBIT_UPGRADE_MAX_CYCLES` (по умолчанию 3: третий подряд не продолжается), запись запуска не найдена, запуск уже завершился сам или его остановил пользователь, запуск помечен не этим намерением или у него уже есть продолжение. Тогда карточка запуска в чате говорит, чем кончился перезапуск: после отката она красная («Перезапуск Orbit не удался и откатился, работает прежний код»), в остальных случаях добавляет «Продолжение не запущено». Тот же путь работает, когда агент сам выполняет `npm run self-upgrade` в своей команде: там, где предлагается `restart_orbit`, команды корневого агента и процессы его CLI получают `ORBIT_RUN_ID`, `ORBIT_CHAT_ID`, `ORBIT_PROJECT_ID`, `ORBIT_AGENT_ID`, `ORBIT_RESUME_FILE` и `ORBIT_USER_DATA` (скрипт сигналит экземпляру этого профиля). Остановка запуска пользователем, пока работает скрипт, отменяет перезапуск: runtime пишет `artifacts/self-upgrade-cancel.json`, останавливает дерево процессов скрипта и снимает его блокировку, а скрипт (между шагами) и наблюдатель (перед записью намерения и перед сигналом) видят отметку и заканчивают со `status: cancelled`, ничего не перезапуская.

**Перезапуск runtime вручную.** «Настройки» → «Runtime» показывают режим, состояние, pid, число перезапусков, время последнего и число необработанных ошибок; кнопка «Перезапустить runtime» запускает новый процесс runtime с кодом с диска, окно остаётся открытым, идущие запуски прерываются. В режиме `inprocess` (новый код runtime там загружает только перезапуск Orbit) и пока runtime запускается или перезапускается кнопка недоступна. То же делает сигнал `Orbit.cmd --restart-runtime` (или `npm start -- --restart-runtime`); `--reload-renderer` перезагружает только окно, `--relaunch` — весь Orbit. Перезапуск runtime ждёт, пока завершится первый старт Orbit, а если файлы оболочки на диске уже изменились, отказывает («shell files changed — relaunch Orbit»): новый runtime не должен работать со старой оболочкой. Вызовы окна во время перезапуска ждут новый runtime до 30 с. Runtime, который упал до готовности (ошибка загрузки кода, таймаут старта, другая версия протокола), сам не перезапускается и остаётся остановленным до перезапуска вручную; упавший после готовности перезапускается сам, не больше трёх раз за минуту. Строка в боковой панели показывает «runtime перезапускается…», «runtime перезапущен за N мс», «runtime упал, перезапускается…», «runtime упал: …» или «runtime остановлен: …», а после необработанной ошибки в работающем runtime (он продолжает работать) — на 6 с «ошибка в runtime (N): …».

**Переменные окружения** (задаются перед запуском Orbit):

- `ORBIT_RUNTIME_MODE=child|inprocess` — runtime в отдельном процессе (по умолчанию при запуске из репозитория) или внутри главного процесса (по умолчанию в собранном дистрибутиве; перезапуск runtime тогда означает перезапуск Orbit целиком);
- `ORBIT_NODE` — Node, которым runtime запускает скрипт самообновления для `restart_orbit` (по умолчанию `node` из `PATH`, иначе Electron в режиме Node);
- `ORBIT_COMPILE_CACHE=1` или путь к папке — кэш компиляции модулей runtime между запусками (по умолчанию выключен: тёплый кэш экономит около 0,1 с старта, холодный стоит секунды);
- `ORBIT_CURSOR_SESSION=1` — сессионный режим Cursor в Full access (вживую пока не проверен, см. [docs/providers.md](docs/providers.md));
- `ORBIT_MCP_CALL_LIMIT_MS` — понизить предел одного вызова инструмента Orbit по MCP (Cursor 50 с, Codex и Antigravity 59 мин); повысить нельзя.

Необязательная проверка с настоящей моделью: `node scripts/smoke-live.cjs`. Она использует текущий вход и модель Codex CLI, расходует квоту и проверяет создание одного подагента, ожидание результата и сохранение истории. Обычные тесты её не запускают.

Для проверки строгого протокола на `gpt-5.6-luna` с `xhigh`: `node scripts/smoke-protocol-live.cjs`. Проверка расходует квоту, запускает шесть помощников в пустой временной папке, проверяет их результаты и отсутствие ошибок протокола; отчёт сохраняется в `artifacts/protocol-live.json`.

Для проверки передачи управления при аудите проекта: `node scripts/smoke-handoff-live.cjs`. Она расходует квоту Luna/xhigh, разрешает чтение небольшого временного проекта и проверяет реальное создание восьми помощников, их результаты и параллельное выполнение. Отчёт: `artifacts/handoff-live.json`.

Для проверки сессионного режима на настоящем Claude Code: `node scripts/smoke-session-live.cjs [модель] [уровень]` (по умолчанию `haiku low`, тратит немного квоты). Агент с ограниченным доступом создаёт файл через инструмент Orbit по MCP одним процессом, затем корневой агент создаёт одного помощника, ждёт его и продолжает ту же сессию с результатом. Отчёт: `artifacts/session-live.json`.
